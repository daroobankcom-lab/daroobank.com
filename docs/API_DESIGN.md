# API design

The local development slice implements `GET /api/v1/search/?q=...` and `GET /api/v1/products/{id}/` for the current package-like presentation model, returning published source-backed fields; search has forward-only cursor pagination with a 30-result per-page cap; it returns no prices or clinical claims. The rest of this document is a proposed contract, not running endpoints. The current implemented public endpoints are described by [OpenAPI 3.0.3](openapi.json), also served at `GET /api/v1/openapi.json`; version compatible changes deliberately. All endpoints over HTTPS, UTF-8 JSON, stable opaque IDs, ISO-8601 UTC timestamps; local source dates and timezone are explicit. The target public API should expose only approved, non-sensitive fields; the development filter is not a governance approval. Handle Persian and English input in Unicode, without leaking draft data.

## Read surface (`/api/v1`)

- `GET /search?q=&type=&cursor=&limit=` searches normalized, published catalog concepts with type and unambiguous package details. Prefix/fuzzy suggestions cannot decide identity.
- `GET /drugs/{id}` and `/drugs/{id}/monographs?audience=patient|professional`: approved version, references, review time and status.
- `GET /products/{id}` and `/packages/{id}`: identity and provenance; `GET /packages/{id}/prices?category=&unit=&cursor=`: approved publication history and source/verification/freshness. Unknown effective dates remain null.
- `GET /manufacturers/{id}`, `GET /safety-alerts/{id}` are gated by approved data. No interaction endpoint returns a safety result before licensed coverage and validation.

List responses: `{ "data": [], "page": { "next_cursor": null }, "meta": { "as_of": "..." } }`; a stable opaque cursor ties to ordering/filter, max page size documented in OpenAPI. Errors: `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`; no stack trace or PHI. Locale formatting belongs to clients, but currency and unit are explicit.

## Internal/admin surface

Versioned authenticated endpoints can create drafts, attach evidence, list ingestion runs/candidates and approve/reject/withdraw after scope, role, state and separation-of-duties checks. Use optimistic concurrency (version/ETag), reason and transactional audit; idempotency keys for externally retried commands. Suggested routes: `POST /admin/candidates/{id}/decisions`, `/admin/content-versions/{id}/decisions`, `/admin/crawl-runs` and `GET /admin/crawl-runs/{id}`. These are design examples, not permission grants. Schedule changes and manual jobs require crawler-operator permission and an audit event; credentials may not be returned.

## Security and evolution

Target: public read rate limiting and admin sessions with secure, HttpOnly, SameSite cookies, CSRF protection and MFA. The current development-only staff session uses Django authentication and CSRF, but has no MFA or rate limiting and is disabled outside debug mode. Institutional/mobile API credentials use scoped short-lived tokens with revocation and rate/usage limits, selected after threat review; no secrets in client apps. No patient data in search queries, logs or public API responses. Compatibility: additive fields only in v1, document deprecations, contract tests and deliberate versioning for breaking changes. Python, mobile and future AI services use this contract rather than shared SQL. Consultation interfaces remain disabled and separately authorized; design them only after legal and privacy approval. Measured contract drift and unbuilt authentication/permission boundaries are documented in [the API and permissions plan](API_PERMISSIONS_PLAN.md) ([ADR 0235](ARCHITECTURE_DECISIONS/0235-api-permissions-plan.md)); no token model or OpenAPI change has been implemented.

## Development endpoint example

`GET /api/v1/search/?q=...` returns `{"data": [...], "meta": {"limit": 30, "candidate_scan_limit": 150, "pagination_available": true, "next_cursor": null}}`. Each result is a package-like presentation with name, manufacturer, strength, form, package description, optional IRC and source URL/name/verification timestamp. The same service backs the HTML search. Empty queries return no records. Only published, dated records with nonblank identity fields, a nonblank source name and a valid HTTPS URL without embedded credentials are returned. This is **not** a real approval system.

For another page, pass `next_cursor` with the same normalized `q` as `GET /api/v1/search/?q=...&cursor=...`. A null cursor means no further SQL candidates were seen. Each request validates up to 150 candidates, returns at most 30 eligible records and fetches one extra candidate for continuation detection. An empty page can still have a cursor when the scan encountered only ineligible records; follow it rather than concluding there are no later results. A SQL match is rechecked against the normalized current fields fetched for that row, so a stale positive can be omitted; stale projections can still hide valid matches and are not repaired. These limits do **not** bound the work PostgreSQL may do to filter/sort the table. Sorting is by database `name_fa`, then numeric PK; database collation affects ordering. This is forward-only keyset pagination, not a snapshot: inserts, deletes, eligibility and name changes between requests can cause skips or duplicates. An update or withdrawal committed after a candidate is fetched can still leave that candidate in an in-flight response; a later request re-reads the database, subject to further changes. A changed, deleted or ineligible cursor anchor, changed query, malformed/tampered cursor or expired cursor yields HTTP 400 `{"error":{"code":"invalid_cursor","message":"Search cursor is invalid or expired; restart the search."}}`; restart from the first page. Cursor lifetime is at most one hour on the verifying host; a future-dated cursor is rejected, so clock skew or rollback between hosts can require a restart. Key rotation also invalidates it. Query is trimmed and truncated to 120 characters as before, then normalized. If this retained prefix contains a Unicode control (`Cc`) or surrogate (`Cs`, possible in a direct service call), the API returns HTTP 400 `{"error":{"code":"invalid_query","message":"Search query contains unsupported characters."}}` before database access; this takes precedence over cursor validation. The HTML search returns a no-store, no-referrer, noindex error page with a blank form rather than echoing the invalid query. Characters beyond the retained prefix are ignored as before; control whitespace stripped at the HTTP query's edges is also not part of the retained prefix. The direct service does not strip before its own prefix check. Other format characters, including Persian ZWNJ, remain accepted; this is not a Unicode-spoofing defense. HTTP decoding may replace invalid byte sequences before validation, and upstream access logs can still retain the raw query.

Cursors are signed, not encrypted. They contain an anchor numeric ID and keyed digests of the normalized query and anchor name, not the raw query or name; an anchor can be a filtered-out candidate. A cursor is not an authorization mechanism or confidentiality guarantee. Do not put personal data into searches: search terms and cursor URLs can appear in access logs. For resolved public search, presentation detail and OpenAPI views, Django applies `no-store`, `no-referrer` and `noindex` to responses, including handled errors, disallowed methods and CSRF rejections. Known public path shapes also receive these headers on slashless redirects, oversized numeric-ID resolution failures and Django's early HTTPS redirects. Other unresolved paths, upstream proxy responses and access logs remain outside scope; redirects still retain the query string, and development debug errors can disclose request information. See [ADR 0044](ARCHITECTURE_DECISIONS/0044-slashless-privacy-boundaries.md). The HTML invalid-cursor page retains the valid query in its restart form but does not echo or resubmit the invalid cursor. The read endpoints also accept HEAD. Other methods can yield 405 (`Allow: GET, HEAD`) or a CSRF 403 before the view; 405 and CSRF errors are not part of the API JSON error schema. Public rate limiting, production-scale indexing and snapshot-consistent export are not implemented.

### Current presentation detail

`GET /api/v1/products/{id}/` returns `{"data": {...}}` with the same fields as one search result; IDs are current numeric database IDs, not yet stable opaque identifiers. A nonexistent, unpublished or ineligible record returns HTTP 404 with `{"error":{"code":"not_found","message":"Presentation not found."}}`. Both success and 404 are `no-store`, `no-referrer` and `noindex`. The HTML counterpart `/products/{id}/` is deliberately noindex and not in the sitemap. Neither endpoint exposes prices, clinical content, availability or review events. Do not interpret a published flag or verification timestamp as evidence of clinical approval, source rights, availability or correctness. Bulk writes can bypass model validation and create stale search projections; read-side checks reduce, not eliminate, risk. Source URLs are displayed to users and may include query strings: never store credentials, personal data or sensitive tokens in them. No source is fetched or rights verified by these endpoints.
