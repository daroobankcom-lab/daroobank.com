# ADR 0003: development-only web intake receipts

Status: implemented for development, 22 November 2026; the no-row-membership decision is partially superseded by [ADR 0004](0004-intake-row-manifest.md). The text below records the original decision.

## Context and decision

Product and price CSV staging previously returned a one-request count summary, with no durable summary of the web operation. Introduce a minimal `ImportReceipt` for successful web staging only. It records domain, asserted source name/URL, actor/time, input row counts and created/duplicate counts; price receipts also capture suggestion counts computed during that request. Counts, receipt and candidate writes use one database transaction, so an error creating the receipt or candidates rolls back that request. DB constraints enforce basic count/domain consistency. A replay creates another receipt even if all rows already exist. The UI lists/paginates receipts and displays details, filtered by the corresponding existing product or price candidate view permission. Detail lookup occurs within the authorized domain; source-only staff cannot see receipts.

Do not retain uploaded file bytes, filename, file hash, row membership or candidate IDs in the receipt. Product and price candidates remain the only detailed records. This decision reduces retained material but makes it impossible to reconstruct the exact batch membership from the receipt. Receipt counts describe input rows, not unique candidates; price suggestion counts include duplicates and are recalculated against the catalog at that time. No evidence, rights verification, final approval or publication is implied. No receipt is written for preview, invalid or failed requests, historical imports, direct calls to the original importer services or CLI imports. Local code can also invoke the receipt wrappers directly with an authorized user, outside the web debug gate. Consequently the absence of a receipt proves nothing about whether an import occurred. No attempt is made to backfill historical events.

## Alternatives and consequences

A full ingestion run/manifest, content hash and candidate-to-batch links could improve traceability, but would introduce retention, privacy, deletion, replay and access-control decisions not yet agreed; they are future work, not silently simulated here. Failure reports, signed records, durable append-only audit, operator permission history, request idempotency keys, source license validation, retention and database concurrency controls are also absent. Model `save`/`delete` guards do not prevent bulk ORM/direct SQL; actor/time are not cryptographically verified. Synthetic test transactions cannot establish production concurrency or resilience guarantees. DB exceptions propagate rather than reporting success. A deployed workflow needs controlled identities, security review and a tested production database before use with real data.
