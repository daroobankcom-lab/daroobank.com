# ADR 0004: development intake row-outcome manifest

Status: implemented for development, 22 November 2026; partially supersedes [ADR 0003](0003-web-intake-receipts.md) on row membership retention. Its other limitations still apply.

## Context and decision

Receipt counts alone could not identify which staged candidates were encountered. New successful web receipt-backed product and price imports retain a bounded row-outcome manifest in the same transaction as candidate staging and receipt creation. Each logical CSV data-row ordinal records the asserted source record ID, candidate payload consistency hash, a candidate FK, whether it was newly created or already present, and for price the suggestion status recalculated for that row at that moment. Multiple identical rows or replays remain distinct manifest rows and can point to the same candidate. Product input remains limited to 1000 rows; price input to 5000. Constraints enforce a positive bounded ordinal, unique ordinal per receipt, exactly one candidate domain and valid status for that domain. The service verifies outcome totals before writing; a write or callback error rolls back the transaction.

Old receipts have a null manifest version: do not invent or backfill membership. A version-1 receipt detail checks aggregate row counts, contiguous ordinals and domain/status totals before showing paginated items, then compares each candidate's source identity and payload consistency with the item before displaying a link. These checks are defensive consistency checks, not cryptographic provenance. Staff see only their permitted domain as before. Candidate pages show at most five recent distinct same-domain receipt links as advisory clues. Output caps do not bound DB scan/sort work.

## Privacy and limitations

The row IDs and candidate hashes add retained operational metadata. No uploaded file bytes, filename, file-level hash or raw CSV formatting are retained. Ordinal is a data-row position, not necessarily a physical line number; the stored data cannot reconstruct the original file. Candidate hashes are not signatures, do not prove data or source authority, and the price payload hash does not cover the source URL. A duplicate is identified by the existing intake rules, not by source authenticity; its actor/provenance remains that of the earlier candidate. Match statuses are request-time suggestions, not approvals. Counts/row relationships can be changed by bulk ORM or SQL, and model guards and FK protection are not tamper-resistant audit. FKs use PROTECT, so retention, deletion and repair need an explicit controlled design; do not bypass them in production.

Previews, failures, original direct importer calls, CLI and older receipts still have no row manifest. Service wrappers can also be invoked by local code outside the web debug gate with an authorized user. Committed same-domain, exact-source staging now cooperatively serializes on PostgreSQL through [ADR 0010](0010-staging-concurrency.md); preview does not. No verification, final approval, network retrieval, scheduler or publication is added. There is no failure log, request idempotency key, signed evidence, retention policy or proven concurrency/crash behavior; production needs source-rights, access, privacy, database and security review first.
