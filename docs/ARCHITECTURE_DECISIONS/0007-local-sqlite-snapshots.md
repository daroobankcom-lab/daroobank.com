# ADR 0007: local SQLite snapshot and isolated restore drill

Status: development-only implementation, 22 November 2026.

## Decision

Provide `tools/sqlite_snapshot.py` as a standalone local utility, separate from web endpoints and Django transactions. `copy SOURCE DESTINATION` creates a new `.sqlite3` file exclusively with owner-only requested permissions, uses SQLite's online backup API to copy committed data (including WAL), and checks `integrity_check` and `foreign_key_check` on the resulting file. It never overwrites an existing file or symlink. If the operation fails it attempts to remove the file it created; a copy left by a crash or filesystem failure must be treated as incomplete. `verify SOURCE` opens an existing file with SQLite `mode=ro` and runs the same checks. Either command needs a trusted local directory, not a directory writable by an attacker. Results and errors omit database rows.

The same copy command can restore a snapshot to a *new*, isolated file for a drill. It deliberately does not replace a live database. A synthetic integration test migrates a fresh application DB, backs it up, restores a separate copy, and runs Django migration and system checks against that copy. Other tests cover WAL, uncommitted data, existing targets and invalid snapshots. The checks do not prove app-level consistency or correct recovery of external files. No automatic schedule, retention, encryption, uploads, public endpoint or production restore is provided.

A minimal GitHub Actions workflow runs dependency, Django configuration, migration drift and synthetic test checks on pushes and pull requests. It has read-only contents permission and does not deploy or store backups. Its third-party actions use major-version tags rather than immutable SHAs; production supply-chain policy, vulnerability scanning, accessibility checks and release automation remain future work. Success locally does not prove a hosted workflow has run.

## Limits

Copies are unencrypted and contain everything, including password hashes, sessions and staff data. Use only synthetic data in development; protect, encrypt and control retention separately. Requested file mode depends on filesystem/platform semantics; directories, SQLite sidecars, exports, external assets and replicas are not managed. SQLite may need access to WAL/shared-memory sidecars when reading a live source. A healthy SQLite check is neither provenance nor a signature, not a clinical/security audit, and does not test application content or migrations. Snapshot copying and verification can consume disk/time; its best-effort deadline applies to backup progress callbacks, not blocked IO or integrity checking. Crash cleanup, hostile local filesystem races, unsupported network filesystems, source loss, disk-full behavior and concurrent load are not comprehensively tested. Production needs its own encrypted off-host backups, documented retention and access, recovery point/time objectives, monitoring, recovery procedures and regular independent drills.
