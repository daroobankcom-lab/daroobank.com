# ADR 0009: PostgreSQL-only database

Status: development implementation, 22 November 2026.

All Django environments use PostgreSQL via psycopg; required database name, user and host come from environment, with password supplied through environment or a supported external authentication mechanism. There is no alternative database backend. `CONN_MAX_AGE` defaults to zero, can be configured to a nonnegative number of seconds and Django's connection health checks are enabled. `POSTGRES_SSLMODE` is optional for local use; enforce appropriate TLS and certificate verification in production. Credentials, roles, network policies and database provisioning are operational responsibilities, not hardcoded application defaults.

Existing Django migrations remain the source of schema; model constraints, FKs and indexes are created by PostgreSQL migrations. The development Compose stack uses PostgreSQL 16, a named volume, a database health check and a bounded application connection wait before migrations and the development server. CI uses a PostgreSQL service and a separate Django-created test database. Tests require a database role with permission to create and drop its test database. These development facilities do not constitute a production deployment or backup policy.

PostgreSQL row locks serialize transactions taking the same `select_for_update` lock, but do not automatically lock absent rows or protect writers that bypass the service. Test coverage includes a concurrent stale clinical review, not a proof for every workflow, isolation level or production load. Bulk writes and privileged SQL can bypass model guards. JSONB enforces valid Unicode and rejects NUL; data imports must be validated before any database migration. PostgreSQL collation can affect ordering, cursor behavior and text matching. All DB engine changes require fresh compatibility, security, load and recovery validation. See [development guide](../DEVELOPMENT_GUIDE.md) and [backup policy](0007-backup-policy.md).
