# ADR 0010: cooperative per-source CSV staging coordination

Status: development implementation, 22 November 2026; extends [ADR 0004](0004-intake-row-manifest.md) and [ADR 0009](0009-postgresql-only.md).

## Context and decision

PostgreSQL unique constraints make a single `get_or_create` robust to a competing insert, but transactions staging multiple overlapping rows in opposite orders can each wait for the other transaction's unique-index entry and deadlock. Preserve CSV order, existing uniqueness rules, callbacks and manifest ordinals instead of reordering source data. Before committing product or price staging, take a PostgreSQL transaction-level advisory lock scoped to the staging domain and **exact validated source URL**. The key is a signed 64-bit prefix of a SHA-256 digest of a versioned namespace, domain and URL. Different domains and URLs normally do not block one another. A hash collision merely serializes unrelated stages; the digest does not prove identity, source rights or authenticity.

The original product and price services acquire the lock after validating the file and opening their transaction, before candidate writes; therefore direct calls, CLI committed staging and receipt-backed web calls use the same protocol. It is retained until the *outermost* transaction ends, including receipt and manifest creation, and is released on commit or rollback. Previews do not acquire it. Input data, candidate deduplication, recorder preservation and callback order are unchanged; replays still create separate web receipts. No scheduler, source access, approval or publication is added.

## Evidence and limits

Synthetic PostgreSQL tests deliberately hold the first transaction while a second stages reversed rows, inspect the waiting advisory lock and validate both domains' counts, actor preservation and ordered manifests. Separate tests cover failure/rollback followed by a waiting stage, direct committed services, previews, scope and savepoints. Clinical concurrent tests exercise two stale additions, the ten-reference cap, and a review racing an addition; a review committed before the addition retains its earlier snapshot, while a review proceeding after it rejects the stale evidence fingerprint.

These locks are **cooperative**, not a database constraint: older application instances, bulk ORM, SQL or code bypassing the staging services can ignore them. Deploy consistently across all writers; do not change the key protocol independently on running workers. Equivalent but differently spelled URLs are different keys. Acquiring another source lock inside a callback or wider transaction can introduce lock-order deadlocks; callbacks must not stage more files or perform external side effects. Transaction lifetime, slow callbacks, database failure and configured database lock/statement timeouts affect wait duration; the app supplies no queue, timeout, fairness guarantee or automatic retry. The hash may collide. This does not prevent matching phantoms, protect product edits, validate rights, make receipts exactly-once, ensure cross-domain consistency, or prove all concurrency and crash scenarios. Test on the actual deployment database and design production isolation, retention and monitoring separately.
