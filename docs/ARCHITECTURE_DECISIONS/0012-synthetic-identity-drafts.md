# ADR 0012: Private synthetic catalog identity assertions

Status: development-only, 2026-11-22.

## Decision

Add a separate, non-public assertion chain: ingredient → formulation with one to five ordered ingredient/strength components → product → package. Each record carries its own asserted source name and HTTPS URL and author; component strengths are positive decimal numerator/denominator and free-text units. Product and package are assertions, not established entities. Nothing automatically links to or changes the existing public `ProductPresentation`, candidate, clinical or price records. The schema in [DATABASE_SCHEMA](../DATABASE_SCHEMA.md) remains a broader target, not the implementation delivered here.

Use `/staff/catalog/identity/` only with the development staff gate, an active staff user, and separate `catalog.view_identityworkspace`, `catalog.add_identityworkspace`, and `catalog.review_identityworkspace` permissions; add and review also require view. Group permissions work. The create forms require a synthetic-data assertion. The create-only formulation form renders a fixed five component slots and validates its management fields and duplicate ingredient IDs before calling the service; the service independently enforces the one-to-five and uniqueness rules. Service functions require the same user permissions but do not enforce the HTTP development gate or checkbox; run them only with isolated synthetic data. Sources are claimed and never fetched; no rights or correctness checks are made. A reviewer cannot be the author of any record in the current chain. Reviews mean defer/reject/refer for further review, not approval. The latest review ID and chain hash are optimistic preconditions; package row locking serializes cooperative simultaneous reviews, one succeeding and the other conflicting.

Payload SHA-256 hashes include actor IDs and content (not timestamps); component order and dependency hashes are included. Review snapshots hold the validated graph. The detail page renders the current chain as labeled fields and checks stored snapshot structure, per-node hashes, links, numeric format and reviewer separation before showing a review; it labels matching versus different historical snapshots, which can be expanded without live-record links. Inconsistent chains and reviews are suppressed in the UI. Creates with dependencies are transactional; components are ordered explicitly. Current graph reconstruction reads components and their ingredients in one joined statement and reuses that result when hashing; related product/formulation rows are joined for the staff list and detail views. Payload and snapshot format remain unchanged. The list is paginated in groups of 20; review history uses descending-ID forward pagination with at most 25 rows per page and a link back to the newest page. Cursor IDs are positions, not access grants or confidential tokens; every request enforces the same staff permissions and package filter. The review form is only offered on the newest page and uses the latest review actually shown, so a newer concurrent submission causes a conflict; after conflict the user must reload and reassess. URLs reject query, fragment and credentials but may nevertheless contain secrets in their path: users must enter no confidential data.

## Limits

This is a narrow prototype, not a complete drug identity schema, matching system, approval workflow, source provenance proof, clinical verification or public publication. The schema does not model salts, equivalence, concentrations beyond free-text units, organizations, variants, regulatory identifiers or lifecycle comprehensively. Units and relationships are not scientifically validated. Values and source/author assertions can be fabricated. Distinct records can describe the same thing; no uniqueness or automated equivalence is implied.

Historical graphs can be coherent but fabricated or recomputed; historical labeling is a comparison, not proof that a real change occurred. No review decision, reason or timestamp authenticity is established. Hashing detects some mismatches, not malicious changes: hashes are unkeyed, a database writer can recompute them and review reason/decision/time are not included. The ORM save/delete guards do not prevent bulk updates/deletes, raw SQL or privileged direct component insertions; DB foreign keys and selected constraints are not immutable audit controls. Pagination is not a snapshot: uncooperative updates/deletes and out-of-order inserts may alter results; query plans and large-dataset performance have not been measured. The review lock coordinates calls using this service only; direct writes, old code and out-of-band changes can race with graph reads, which are not an isolated snapshot across the whole graph. The component read improvement is not a global locking or repeatable-read guarantee; callers can also pass stale model instances. See [ADR 0013](0013-synthetic-package-revisions.md) for limited package correction links; these are not covered by package reviews. No global concurrency, audit, retention, privacy, legal, clinical, accessibility or production security certification is claimed. The public catalog's publication rules are unchanged. Do not enter real patient, proprietary or regulated data.
