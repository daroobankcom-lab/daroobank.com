# ADR 0013: Private package correction branches

Status: development-only, 2026-11-22.

## Decision

An existing synthetic `IdentityPackageDraft` can be used to create a new package assertion and a separate `IdentityPackageRevision` immediate-parent link. The original record, graph and reviews are not changed; reviews are not copied, and the new package can be reviewed independently. The link is an **assertion of correction**, not proof that the two packages are identical, equivalent, authorized or clinically correct. The same product and validated product graph must be retained; for a different product, make an independent package assertion. The user must give a change reason and change at least one package or source field. Corrections to ingredient, formulation or product are addressed separately in [ADR 0014](0014-synthetic-component-revisions.md); they do not automatically update packages.

The operation requires active staff with both `catalog.view_identityworkspace` and `catalog.add_identityworkspace`; the web route is behind the existing development-only staff gate, CSRF and private headers, and requires the synthetic-data checkbox. Direct service calls enforce permissions but are outside the web gate and checkbox. The form shows the current parent and latest preliminary review, when internally consistent. A corrupt current graph or corrupt latest review blocks correction. Optimistic preconditions are the graph hash and the latest parent review ID actually read when the form was prepared. The service locks the parent row and checks both preconditions in a transaction; it then locks/validates the product through the existing package creation service and atomically creates child and link. A conflicting parent review results in a conflict and reload; form content is not retained. The preconditions are concurrency checks, not proof that a user read or understood the review.

Concurrent corrections from the same parent may produce separate branches. No branch is automatically current or preferred. A PostgreSQL check requires a parent ID lower than its child ID; the child has at most one incoming link, preventing ordinary cycles. Link data hashes the immediate IDs, authorship, change reason and the parent/child graph hashes. Detail pages show a link and reason only if its fields and the current immediate parent and child graphs agree; otherwise they show an inconsistency warning. Immediate children use descending-ID pages of ten, scoped to the parent; cursor IDs are not access grants and the history is not a consistent snapshot. Only the immediate link is checked, not the full ancestry. A changed/broken current graph can make an old link unavailable rather than proving when it changed. No existing package is backfilled into a revision.

## Limits

These links and hashes are unkeyed and not signatures, durable audit or authenticity proof. Bulk ORM/SQL and privileged direct insertions bypass service/model guards and can fabricate or recompute links; direct writers can race graph reads. The parent lock only coordinates cooperating review and revision services for that package; it does not establish global isolation, authorization of sources or source rights. The review history precondition is not stored as evidence of what the editor observed.

Package reviews attest only the current package graph, not the revision link or parent. The reviewer is distinct from authors of that current graph; a parent-only author is not automatically excluded. Parent reviews do not carry forward and a new review is not clinical approval. Future requirements for review of revision provenance and whole ancestry need a separate design and migration; do not treat this as complete version governance. Data is private and synthetic only; no public catalog, price, clinical record or publication behavior changes. Query plans, browser/accessibility, production security, medical and legal validation remain unperformed.
