# ADR 0016: bounded technical inspection of synthetic clinical drafts

Status: development-only implementation, 22 November 2026; query strategy superseded by [ADR 0017](0017-batched-clinical-inspection.md), and author-presence semantics extended by [ADR 0056](0056-clinical-inspection-author-presence.md). Builds on [ADR 0005](0005-clinical-draft-triage.md) and [ADR 0006](0006-clinical-evidence-assertions.md).

## Decision

Add a read-only page at `/staff/clinical/inspection/`, behind the existing DEBUG-only staff gate and `clinical.view_clinicaldraft`. It enumerates existing draft IDs and fixed technical statuses, with links to the already-permitted details; it does not display draft text, reference details, authors or hashes in the report. It neither changes permissions nor performs writes or network requests. Invalid position/category yields the existing private non-reflecting 400 page with a fixed restart link.

Scan up to 50 drafts in ascending ID order, with one lookahead, then apply the optional status filter to that batch. The next position comes from the last scanned row even if the filter yields no matches. Each draft is checked with the existing `valid_draft` (payload and immediate parent only). If invalid, supplementary assertions are not examined. Otherwise the set is classified as available, invalid or over limit, using the checks shared with `evidence_state` and its existing bound of 11 assertions for a limit of 10 and recorder-existence check. Over-limit takes precedence over assertion validation. Available only means these checks found no inconsistency. No review or historical snapshot is assessed.

## Consequences and limits

Originally, the maximum was one draft query plus up to two queries for each valid draft (assertions and, when needed, recorders): at most 101 SELECTs per request and 11 assertion rows retrieved per examined draft. The current batch strategy is documented in ADR 0017. Neither strategy bounds bytes, database scan/sort effort, time, or production load; neither is intended for production monitoring. Queries are separate and no consistent snapshot is taken, even within a response; concurrent edits can change findings, and inserts behind the cursor or later changes can be missed. A next link indicates a lookahead at query time, not a promise of future rows. Results enumerate private IDs and technical status, so granting view permission has that consequence.

Hashes are not signatures, can be fabricated by privileged DB writers, and do not bind all metadata. The checks do not establish the author's existence, full ancestry, review validity, authenticity, evidence quality, source availability/rights, safety or clinical correctness. Absence of findings is not approval or a completeness guarantee. It does not repair, publish, verify, audit, or change a clinical workflow. Alternative database-wide aggregation or a repair queue was rejected because it implies global completeness or actionable authority that the underlying synthetic data and checks do not provide. Real clinical content remains out of scope.
