# ADR 0024: explicit one-row synthetic projection repair

Status: development-only local command, 22 November 2026; extends [ADR 0023](0023-presentation-partial-save-projections.md). Selected write conflicts are handled as described in [ADR 0063](0063-projection-repair-conflict-boundary.md). No production workflow, source verification or audit is provided.

## Decision

Provide `repair_catalog_projection` for explicit repair of **one** presentation in the default database. It is disabled unless `DEBUG` is enabled. The default invocation is read-only and reports only the internal ID, fixed status and affected projection field names. For a safe, inconsistent row it returns a signed token with keyed state/database fingerprints and a ten-minute lifetime; it intentionally contains no product fields or source URL. A consistent or unsafe row has no token. Source identity fields must have bounded lengths, no control/surrogate characters and nonempty normalized required values; normalized IRC must fit its 80-character column and the normalized search projection and stored search projection must each fit 8192 characters. Unsafe input is not automatically repaired. This check is intentionally narrow and is not model, source, medical or license verification.

Commit requires the same ID, `--commit`, the preview token and `--confirm-synthetic`; the latter is an operator assertion, not proof. The service requires the actual boolean `True`. Validate token format, signature, expiry, a non-future timestamp, ID and keyed database-configuration fingerprint; clock changes can invalidate tokens. Then lock the row in an atomic transaction, reread all fields, recompute both projections and compare a keyed fingerprint of the entire stored row and expected projections. Datetime microseconds are retained. Reject deleted, changed, unsafe, already-repaired, expired or mismatched observations. If valid, update only the differing `search_text` and/or `irc_normalized` columns. No model `save()` or save signals are invoked; no provenance, identity, publication flag, source or review fields are changed. Failures inside the transaction roll back. When the service is called inside an existing outer transaction, the returned status does not mean that outer transaction has committed. No web endpoint, batch repair, background task, automatic rewrite or migration is added.

## Consequences and limits

Repair can change which existing published rows search returns or how price suggestions match. It does not approve or publish anything, establish correct product identity, prevent duplicate matches, validate rights or authorize real-data use. Preview and token do not guarantee later outcomes: additional writes after commit may cause new drift, and state changed and restored to exactly the same values cannot be detected (ABA). Locks can wait or fail; there is no retry policy. The limits bound one row and chosen character counts, not SQL work, bytes read, normalization cost or runtime. Read-only quality scanning still does not provide complete coverage or repair records.

The token is signed, not encrypted; it exposes an ID and keyed fingerprints, not raw fields. It is not an authorization credential or tamper-proof audit. The development secret may be known, configuration binding is not a globally unique database identity, and DEBUG/confirmation do not prove that a database contains only synthetic data. Local OS, database and secret-key access remain authoritative. CLI arguments, output, shell history, logs and process listings may expose tokens and identifiers. No user identity, durable repair log, approval separation, recovery, monitoring or production concurrency/security guarantees exist. Use only isolated synthetic development databases; design access control, backup/restore, provenance and audit before considering real data. Tests cover selected interleavings and failures, not all database schedules or versions.
