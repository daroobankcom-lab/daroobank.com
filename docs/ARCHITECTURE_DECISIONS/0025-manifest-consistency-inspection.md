# ADR 0025: bounded receipt-row consistency inspection

Status: development-only, read-only inspection, 22 November 2026. Extends [ADR 0004](0004-intake-row-manifest.md); it does not create provenance or verify an import.

## Decision

Provide a private inspection page for one receipt at `/staff/operations/imports/<id>/inspection/`, linked from receipt detail. Active staff need the existing view permission for that receipt's candidate domain; a user with only the other domain sees 404, and users without either domain are denied. The normal DEBUG-only staff middleware and private no-store/noindex headers apply; only GET/HEAD are allowed. Service-level permission checks use the same domain rules, and receipt IDs are validated before the receipt lookup. Local callers can invoke the service outside the web DEBUG gate, so this is not a production boundary. Invalid inputs get a private non-reflecting error and a restart link only after the authorized receipt has been resolved.

The page first reuses the same aggregate manifest-structure check as detail. A synthetic PostgreSQL test now demonstrates a real separate-connection deletion between that aggregate and the later batch read: one response can report `available` with no rows, while a subsequent scan reports `invalid`. The test documents this limitation, not a requirement to preserve it; it must be revisited if isolation changes. Legacy receipts remain `legacy`, and structural inconsistency stops row inspection; neither is reconstructed. For an available manifest, one query retrieves at most 50 ordered items and one lookahead joined to the appropriate candidate. Each scanned item's current candidate is checked with the same shared bounded row/candidate consistency predicate used by detail. Output contains only the receipt ID, data-row ordinals, fixed technical categories, batch counts and forward position; no source names, URLs, original fields, record IDs, hashes or candidate IDs are rendered. An optional category is applied **after** each batch, so an empty filtered page can still have a next page. Starting ordinal accepts 0–5000; manual positions can skip rows. The ordinal is a logical data-row position, not necessarily a physical line number.

The checks compare the stored row's source identifiers/hash with the current candidate and validate its current bounded structure and derived fields; they do not recompute the historical price suggestion or compare it to a later candidate status. The `consistent` label means only that these limited checks detected no mismatch. A warm-permission available request uses three SELECTs: receipt, structural aggregate and bounded candidate join. Legacy needs one and invalid structure two. These are synthetic operation counts, not production benchmarks; permissions may issue extra queries and aggregate/database filtering and sorting work, bytes, validation CPU and elapsed time are not bounded by the output cap.

## Limits

Receipt lookup, aggregate and item/candidate join are separate reads and pages are separate requests: no snapshot or completeness guarantee exists. Concurrent or bypassed edits can change or remove rows after structural validation, including an available report with no scanned rows; a later request may find a different status. Bulk ORM/SQL can bypass model guards or fabricate consistent-looking data. Missing references, malformed fields, mismatched hashes or source identities yield a fixed inconsistent status where observable, not evidence of wrongdoing. A hash is not a signature. Neither this page nor its absence of findings verifies file authenticity, source authority/rights, product identity, historical suggestion, reviewer qualifications, prices, clinical content or release readiness. No data or public content is changed; use only synthetic non-sensitive data.
