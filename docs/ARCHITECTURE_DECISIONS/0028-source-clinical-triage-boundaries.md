# ADR 0028: source and clinical triage input and concurrency boundaries

Status: development-only, 22 November 2026. Extends the source-claim and synthetic clinical-draft workflows; does not add authorization or publication.

## Input decision

Source-claim triage now requires a positive actual integer claim ID within PostgreSQL bigint range. Source and clinical triage require an actual integer expected-review ID from zero through the bigint maximum; booleans, strings, negative values, out-of-range values and non-string decisions are rejected before the transaction. Staff authorization remains first. A missing source actor now raises `PermissionDenied`. The source and clinical hidden expected-review form fields have the same upper bound; a malformed web submission is HTTP 400, a syntactically valid but stale review expectation remains 409. The normal valid flow is unchanged. Before this change, direct source review could treat `True` as ID 1, and unhashable decisions in both services could raise `TypeError`. Large expected-review values were treated as stale rather than rejected as malformed.

If the hidden review ID is invalid, both detail responses show a Persian recovery notice and an explicit link to the appropriate detail GET. The user's submitted form is not preserved when they follow it, and this notice only covers that hidden field, not every error or conflict. It is not a redirect to an arbitrary user-supplied destination. Bound hidden fields and existing validation errors remain in the private response; do not submit sensitive values. Permissions, privacy headers and CSRF are unchanged. Synthetic service and HTTP tests cover malformed types and bounds, authorization ordering, no business queries for invalid direct input with warmed permission cache, valid zero and stale maximum. Selected Chromium tests exercise both recovery links with no successful review.

## Selected concurrency observations

PostgreSQL tests on separate connections, using barriers, explicit events and bounded lock/statement timeouts, check that two source reviewers using the same expected version produce one event and one conflict. They also check a competing claim update blocks review and is rejected after commit, a review blocks a competing claim update until its transaction finishes, self-review is rejected, and a failed event write rolls back. Direct/bulk updates can bypass model guards after the lock is released. These tests do not prove all schedules or writers participate.

Clinical tests similarly check two reviewers with one expected version. Existing tests cover cooperating reference additions and the shared draft lock. A new deliberate bypass test pauses review after reading reference state while holding the draft lock, then updates an existing reference and its fingerprint consistently through a separate bulk ORM writer that does not lock the draft. The bypass commits before review resumes; the review succeeds with its prior internally coherent snapshot while current evidence is also coherent but different. The clinical detail page warns that concurrent or later changes, especially outside the application protocol, can make a review snapshot stale. The test exposes a permitted limitation; it is not a concurrency fix, and the user-facing status comparison is a later read rather than guaranteed real-time detection.

## Limits

No table, predicate or child-reference lock, retry strategy, serializable transaction, writer protocol enforcement or audit is added. Privileged database and bulk writers can bypass guards and produce other states; later changes can always stale a review. Results are for selected schedules on the test PostgreSQL setup, not all races, deployments or failures. Hashes are reproducible consistency checks, not signatures. Source claims and preliminary triage do not establish rights, source authenticity, medical correctness, professional approval or publication permission. Only synthetic, nonconfidential data is suitable for the development system.
