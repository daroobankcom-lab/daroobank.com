# ADR 0029: lock existing clinical reference rows during writes

Status: development-only, 22 November 2026. Parent-lock limitations below describe the historical state; [ADR 0030](0030-clinical-immediate-parent-locks.md) supersedes that specific race. Narrows the specific bypass race observed in [ADR 0028](0028-source-clinical-triage-boundaries.md); it does not establish snapshot isolation or clinical approval.

## Decision

Within the existing PostgreSQL transaction, clinical review and supplementary-reference addition first lock the draft as before, then read the first 11 references ordered by PK with `SELECT FOR UPDATE` before validation, fingerprint comparison, deduplication and write. For ten or fewer rows, the existing reference rows included in that read are locked until the outermost transaction ends. Eleven is an over-limit sentinel: the operation fails without a write and locks are released on rollback. The `evidence_state` read-only callers retain their ordinary non-locking query; they may observe a different committed state and do not wait for an ordinary row update. No extra SQL query is introduced by the lock, but the lock itself adds database work and waiting.

A test first reproduced ADR 0028's existing-reference race without the lock: a nonparticipating writer updated a reference after the review read and before its commit. With the lock, selected PostgreSQL tests show that an ordinary concurrent bulk update of an included reference waits; a test timeout aborts that writer, then a later update succeeds after review commits and makes the snapshot stale. Tests also coordinate a pre-existing updater and verify a waiting review and addition observe the committed change and conflict on the old fingerprint; exercise rollback/outer transaction lock lifetime and the over-limit sentinel; and show ordinary read-only observations do not take these row locks. The bounded query locks the first 11 rows, not a twelfth. This is a selected interleaving, not a proof against every SQL operation or deployment.

## Remaining boundaries

`SELECT FOR UPDATE` does not lock absent rows or an arbitrary predicate. A nonparticipating transaction with deferred constraints can create an uncommitted new reference while review is in progress, and commit it later; a test demonstrates the review snapshot becoming stale after that later commit. Constraint enforcement, isolation configuration, administrative disabling of constraints, direct SQL and other paths require separate analysis. The lock also does not lock the draft's immediate parent or users. Another selected test demonstrates a direct parent update after validation while the child review holds its own draft lock: the review can succeed while the current child subsequently fails its immediate-parent check. Parent and whole-graph consistency remain unresolved. Existing snapshots can always become stale after commit; the UI warning remains.

Acquiring draft then reference locks can increase wait time and introduce deadlocks with code that locks in a different order; there is no timeout or retry policy in the application. The test-specific timeouts are not production settings. Eleven returned rows bounds neither SQL scan/sort work, bytes, total lock wait nor runtime. The tests run on synthetic data at the test database's default isolation and cover only chosen schedules. This is not tamper resistance or a replacement for a database-enforced writer protocol, authentication, source rights, independent medical review, audit, approval or publication. Real-data and production use remain out of scope.
