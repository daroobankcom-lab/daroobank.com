# ADR 0030: lock the immediate clinical draft parent during selected writes

Status: development-only, 22 November 2026. This supersedes the specific unprotected immediate-parent writer race described in [ADR 0029](0029-clinical-reference-row-locks.md), not its other limitations.

## Decision

For review and supplementary reference addition, first lock the subject draft, validate its own payload, then separately fetch and `SELECT FOR UPDATE` its immediate parent before validating the pair. Revision creation first locks the selected prior draft, then applies the same check to that draft and its immediate parent (the new draft's grandparent). A root needs no parent query. A missing parent or invalid payload fails closed. The helper requires an atomic block; its caller is responsible for holding the subject row lock. Parent data is fetched *after* obtaining the lock, rather than relying on a `select_related` object read before waiting. Reference rows, where relevant, are subsequently locked as in ADR 0029. The immediate parent and the reference locks last until the outermost transaction ends, not just the service's inner atomic block. Ordinary readers retain their non-locking behavior.

For a valid link, the parent ID is strictly smaller than the child ID before the parent lock is requested. Participating draft writers therefore acquire the subject and then the immediate parent in descending ID order. Sibling operations may serialize on the shared parent. The guarded validation does not recurse: it checks the immediate parent's own payload, not that parent's relationship to its own parent. Revision from a root only locks the selected prior draft. There is one extra parent SELECT for a non-root subject; this is not a benchmark or a bound on database work or wait time.

## Evidence and boundaries

Selected synthetic PostgreSQL tests cover parent updates waiting while each of the three operations holds locks, and the reverse schedule: an earlier updater commits, a waiting writer reads the new parent and conflicts without writing. Tests also cover stale preloaded objects, missing parents, rollback, outer transactions, sibling serialization, root versus child queries and ordinary non-locking readers. A separate selected test updates the grandparent while a grandchild review runs: the review may succeed although the intervening child no longer validates against its parent. A bypass update after a writer commits can invalidate the observed pair. These are selected interleavings at the test database's default isolation, not an exhaustive concurrency proof.

No predicate, absent reference, whole ancestry, users or external systems are locked. Deferred inserts of references and other nonparticipating or direct SQL paths retain the limitations in ADR 0029. Model immutability is not database tamper resistance. Cycles and invalid parent ordering are rejected by payload checks for the subject, but administrative constraint changes and arbitrary SQL are outside this protocol. Even consistent payload hashes are not signatures, provenance, source rights, clinical validation or an audit.

Lock ordering reduces one obvious cycle among these participating draft writers; it does not guarantee deadlock freedom. Other code, foreign-key checks, bypass SQL or a surrounding transaction can hold locks in another order. Shared-parent contention increases waiting; the application has no lock timeout, automatic deadlock retry or production policy. Test-only timeouts do not change that. No claim is made about deployments using different databases or isolation settings. Synthetic development data only; this is not a clinical approval, publishing or production feature.
