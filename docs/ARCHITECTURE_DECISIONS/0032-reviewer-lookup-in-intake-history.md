# ADR 0032: bounded reviewer lookup for private triage histories

Status: development-only, 22 November 2026. Missing source and clinical creators are subsequently addressed in [ADR 0033](0033-missing-source-and-clinical-creators.md). Extends the missing-reviewer handling introduced for clinical detail in [ADR 0031](0031-clinical-detail-review-comparisons.md) to source-claim, product-candidate and price-candidate detail histories.

## Problem and decision

These three pages previously loaded their 25 latest reviews with an inner reviewer join. A deliberately corrupted or deferred missing reviewer FK could hide a review row, causing the form's expected latest ID to fall back to an older visible event or zero. A selected synthetic PostgreSQL test reproduced the hidden newest row in each domain. The existing service still separately checks the actual latest ID under its candidate/claim lock, so a stale form conflicts; the missing join did not itself bypass that check.

Use a shared helper for these three pages and clinical detail: callers first authorize and scope an unsliced queryset to the one parent. The helper clears `select_related`, fetches at most 25 rows ordered by descending PK, then separately fetches existing reviewer accounts for the distinct IDs on the same DB. It leaves absent reviewers attached to their review row as unknown, not omitted; the row ID remains the expected latest ID. The three intake pages show a fixed missing-account notice and suppress decision, reason and price snapshot details for that row. Available reviewer accounts preserve the existing display. Clinical detail retains its separate technical classification from ADR 0031. No data or permission model is changed. An absent prior reviewer does **not** by itself prevent a new permitted review: tests exercise a stale 409 and a fresh successful review, not a new integrity policy.

## Evidence and limitations

Synthetic PostgreSQL web tests cover missing newest/older reviewers, bounded order and 25-row cap, per-domain privacy and authorization, stale conflict and successful fresh review, and a reviewer lookup with no per-row query. A deferred FK corruption is restored before the test transaction ends. The helper issues one review SELECT and, when IDs exist, one account SELECT; 25 displayed reviews do not mean bounded database scan work, response bytes, JSON size or time. Price review history uses its stored snapshot, not a joined product object. Tests verify the helper clears a previously requested reviewer join and the empty queryset behavior. Synthetic Chromium checks normal source, product and price history at four widths and runs selected axe checks; it does not exercise a permanently corrupted live DB.

The account query and review query are separate non-snapshot reads. A selected test mutates a reviewer ID between those reads and observes a stale account until the next read. An account found now does not establish its historical identity, activity, role or qualifications. Outside clinical detail, this helper does **not** validate review decisions, reasons, snapshots or their hashes, and cannot establish source rights, provenance, audit or approval. Missing submitters/authors in the parent detail or other views, bypass SQL, later changes, incomplete history, other related objects and corruption of actual reviewer rows remain outside this change. Review metadata and hashes are not authenticated. No production, accessibility-across-devices or clinical guarantee is made; use synthetic, non-sensitive data only.
