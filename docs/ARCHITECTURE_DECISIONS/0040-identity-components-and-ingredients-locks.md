# ADR 0040: bounded identity component and ingredient row locks

Status: development-only, 22 November 2026. Extends selected graph-writer checks and narrows the component/ingredient limitations in [ADR 0039](0039-identity-package-formulation-lock.md), not a whole-graph or database-isolation guarantee.

## Problem and decision

Selected PostgreSQL races had shown that a package review could save a graph while an existing component or ingredient changed after the graph read. The ordinary model guards can be bypassed with bulk ORM or SQL. The same exposure existed in other services that build a graph from a formulation.

For package review/correction, dependent product/package creation and formulation/product correction, the service first obtains the applicable parent locks (package, then product, then formulation where present). After the formulation is locked, it locks existing component rows ordered by primary key, selecting at most `MAX_COMPONENTS + 1` (six); zero or more than five conflicts. It then locks the referenced ingredient rows in primary-key order, using a separate bounded query, and conflicts if any ingredient is missing. The writer reconstructs and validates the graph again **after** these locks. Existing formulation creation already locks selected ingredients in primary-key order; ingredient correction locks its subject. Nested creation inside a correction may re-acquire locks and run checks more than once. These row locks persist until the outer transaction ends.

The sixth row is a defensive sentinel for bypassed constraints, not an extra valid component. A five-component graph requires at most five distinct ingredient locks. The existing database ordinal bounds and uniqueness normally prevent a sixth committed component; the bounded selection alone does not bound database work, bytes, or time. Relevant permissions, self-review, optimistic hash/review and creator-presence rules remain. If a graph is missing or inconsistent, no requested write occurs. This is not a repair or authenticity check.

## Evidence and limits

Synthetic separate-connection tests exercise component and ingredient update contention in both directions across package review/correction, dependent product/package creation, and formulation/product correction. They check rollback on missing ingredients/components, selected outer transaction lifetime, bounded ordered SQL, deletion of the sole component before each selected writer acquires its lock, an immediate-FK insert blocked while a review holds its formulation lock, and two simultaneous package reviews whose distinct formulations share ingredients in reversed component order. This selected ordering test is not proof of deadlock freedom. A selected deferred-FK test inserts an additional component in another transaction after review's graph read; the review commits first and the insert then commits, leaving a stale review snapshot. Separate same-transaction test-only bypasses can mutate or add rows after the graph read even while the writer owns locks. These selected schedules do not cover every concurrent deletion, constraint mode or interleaving.

Row locks are not predicate or gap locks. New rows, changed data after commit, bypasses inside the same transaction, user-account changes, older correction ancestry, ABA, other domains, and unsupported database configurations remain out of scope. Locks can increase latency or deadlocks and no automatic retry is added. The account lookup and other reads do not provide historical authorization, source rights, attribution or a consistent audit snapshot. Use synthetic data only; no clinical approval, publication or production-readiness claim is implied.
