# ADR 0043: isolated synthetic PostgreSQL restore drill

Status: development-only, 23 November 2026. This adds an opt-in automated test of a narrow restore procedure, not a production backup service or operational recovery policy.

## Decision

CI and a documented optional local command run `daroobank.test_synthetic_restore` under dedicated `restore_test_settings`. The settings assign a fresh randomly named PostgreSQL **test** source database and reject `--keepdb` and `--parallel`. The test verifies the settings marker and source-name shape before touching the database, seeds only synthetic identities and a preliminary review, and creates a separate randomly named target with `CREATE DATABASE`. Only a target whose creation returned successfully is dropped. The database role must be permitted to create and drop test databases. Never point the exercise at a production or valuable PostgreSQL cluster: name checks and random names are safeguards, not a substitute for server isolation. Django's test runner controls the source DB lifecycle and can delete a colliding test DB, so this must be a disposable test cluster.

With `pg_dump` and `pg_restore` on PATH, the test creates a custom archive inside a private temporary directory, with a pre-created mode-0600 file; lists it; attempts to restore one truncated copy using `--single-transaction --exit-on-error`; and verifies that a selected table is absent after that failed attempt. It then restores the original into the new target, runs `manage.py check` and `migrate --check` against that target, and checks the restored synthetic graph, reviewer, relationship and fingerprint through a separate Django ORM subprocess. It checks the source still has the expected review. Commands use argument arrays, no shell, no password in arguments, a closed stdin and bounded subprocess waits; captured command output is not included in assertion text. Connection credentials may still be visible in process environments to privileged local users, and the dump is unencrypted. A crash or interruption can leave temporary files or test databases requiring explicit identification and cleanup; no force-drop is used.

## Evidence and limits

PostgreSQL 16 local tests exercise successful and truncated-archive cases, cleanup following a simulated dump failure, and preservation of a deliberately pre-existing synthetic target on name collision. Lightweight guard tests check settings names, rejection of reuse/parallel flags and rejection before database access when the marker or source name is wrong. CI runs the same isolated drill with client commands in the PostgreSQL 16 container image over the runner host network, mounting its temporary directories. These tests verify one synthetic database, archive, corruption and graph, not recovery of all records, concurrent backups, application assets, roles, extensions, cluster configuration, production compatibility or point-in-time recovery. `migrate --check` checks pending migrations, not clinical or data correctness. A newer server may require a newer client.

No encryption, off-host retention, cadence, monitoring, backup ownership, RPO/RTO, external-object recovery or authorization is established. The archive is not source provenance, an audit, or verified clinical data. Users must define and test an appropriate production recovery policy separately; no production-readiness claim is made.
