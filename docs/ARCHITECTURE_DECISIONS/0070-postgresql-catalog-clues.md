# ADR 0070: selected read-only PostgreSQL catalog clues

Status: development-only implementation, 23 November 2026. The later [ADR 0072](0072-postgresql-foreign-key-behavior.md) adds limited FK deferrability and database-action clues, [ADR 0073](0073-postgresql-unique-key-clues.md) adds selected unique-key clues, and [ADR 0074](0074-postgresql-check-constraint-names.md) adds named-check presence clues, superseding those specific limitations below.

## Decision

Provide `python manage.py inspect_postgresql_schema` for the configured default PostgreSQL database, only when Django DEBUG is enabled. It executes one parameterized SELECT against PostgreSQL catalogs and reports fixed JSON keys and aggregate counts: managed model and implicit many-to-many tables plus `django_migrations` expected by the current code; unresolved names; names resolving to a non-table relation; missing single-column model-declared foreign keys between managed tables; unvalidated table constraints; indexes not valid, ready or live; and disabled triggers (including internal triggers) on resolved tables. A foreign-key match requires the expected source and target tables and columns, not a particular constraint name. A selected issue yields `attention` and a nonzero command exit; a clean selected result is `no_selected_issues`, not a health certificate. No table/constraint/index/trigger names or application data are emitted. Unexpected database errors produce a generic command error, though the chained exception remains available to local debugging.

The names resolve through the connection's active search path; the resulting catalog observations share one SQL-statement snapshot. Only currently managed model tables and migration history are in scope, not unrelated tables, other databases, child partitions or arbitrary schemas. The command performs no repair, validation, migrations, table locks or application data changes. Catalog reads and connection setup are not guaranteed to complete quickly. Schema changes concurrently in progress, especially concurrent index builds, may produce transient warnings. Treat the result as a prompt for an authorized operator to investigate, not a reason to automatically alter a database.

## Evidence and limits

On a disposable PostgreSQL test database, tests create an actual NOT VALID constraint, a disabled trigger, an invalid index left by a failed concurrent unique-index build, a view and an unresolved name, then remove or roll them back. Separate rolled-back DDL tests remove an expected foreign key or replace it with a key to the wrong target. A separate test demonstrates out-of-scope defects are not reported. The clean command and fixed output, nonzero anomalies, DEBUG gate and sanitized database error are checked. CI runs the command after migrations.

A clean result does **not** compare full column/constraint/index definitions to migrations, check foreign-key actions or deferrability, validate data, find missing non-FK constraints or indexes, verify backups, audit actors, test restore, detect all index corruption, examine privileges, compare replicas, prove schema provenance or assess production readiness. Expected FKs derive from current model metadata rather than the applied migration graph; unmanaged/external targets and composite or non-model FKs are not checked. No production role, security policy or deployment configuration follows. Only run against an authorized synthetic development database and independently restrict access; DEBUG is a development guard, not authorization.
