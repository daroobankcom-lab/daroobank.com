# ADR 0103: selected PostgreSQL auto-sequence settings

Status: development-only implementation, 24 November 2026; extends [ADR 0093](0093-postgresql-auto-field-generation.md) and [ADR 0094](0094-postgresql-serial-default-clue.md).

## Decision

For supported managed Django auto fields, implicit many-to-many keys and the migration recorder, the existing single read-only catalog statement now counts owned sequences with a nonpositive increment, a minimum below one, or cycling enabled. Any count yields `attention` without returning names or values. This is a conservative clue: an intentionally configured sequence can be flagged even if it has not generated an invalid or repeated value. Missing ownership or generation continues to be reported by the existing separate check.

The check deliberately does not enforce an exact increment, start, maximum or cache size, compare migration intent, read the current sequence value, check privileges or compare values with existing rows. It cannot establish that IDs represent commit order or guarantee future inserts succeed; a valid-looking sequence can be rewound, exhausted or altered after inspection. The result observes one statement on one connection, is not a database health certificate and performs no repair. Use only authorized synthetic development databases.

## Evidence

Rolled-back PostgreSQL 16 tests flag cycling, negative increment and zero minimum on a selected model sequence, as well as cycling on an implicit many-to-many and migration-recorder sequence. A 12-case truth-table test covers combinations of negative or positive increments, zero or positive minimum and cycle/no-cycle. A legacy owned sequence with an unusual quoted name is accepted when ordinary and flagged when cycling. A positive nonunit increment remains unflagged, illustrating the selected scope. A separate synthetic sequence with maximum two and cycling returns 1, 2, 1; another has ordinary selected settings but is rewound so an insert collides while the inspector still reports no selected issues. Two-connection tests demonstrate that a cache of three can yield committed IDs 1, 4, 2 in that order, and that even the default cache of one can reserve ID 1 before ID 2 but commit it later. Both pass the selected settings check, which is not a chronological guarantee. Command privacy, one-statement/read-only execution and clean-schema checks remain tested. A small local PostgreSQL 16.2 `EXPLAIN ANALYZE` probe interleaved 30 executions each of the previous `0bd5159` inspector and the current inspector on the same 31-table, 30-auto-field synthetic database while other tests ran. Execution medians were 59.606 ms and 61.557 ms respectively; sample p95s were 102.339 ms and 103.706 ms. Median planning times were 4.319 ms and 5.599 ms. This cached single-machine sample excludes client/ORM overhead and does not establish a general performance bound or causal effect. The examples do not prove all sequence behavior, isolation schedules or PostgreSQL versions.
