# ADR 0110: selected read-only PostgreSQL session-access clues

Status: development-only implementation, 24 November 2026.

## Decision

Provide `python manage.py inspect_postgresql_access` for authorized synthetic PostgreSQL development databases with `DEBUG` enabled. It executes one read-only SELECT and returns fixed JSON keys with aggregate counts, not role names, table names, grants, rows or connection addresses. It reports whether current and session role names differ; current-role and session-role PostgreSQL superuser, createdb, createrole, replication and bypass-RLS attributes; whether the current role has CREATE on the current database and on the `public` schema (null if absent); the server-observed connection transport; transaction read-only setting; and selected managed-table counts for table-level SELECT, INSERT, UPDATE, DELETE and TRUNCATE privileges and enabled/forced row-security flags. Expected names are the current managed model tables plus Django migration recorder; unresolved names and resolved non-tables are counted separately. Resolution follows this connection's search path; all observations come from one statement snapshot.

The command reports observations, not a pass/fail assessment: privileged development roles can legitimately have broad access. A PostgreSQL error yields a generic command error, but its chained exception and ordinary server or local logs may expose details. No role, grant, policy, schema or data is changed. The output itself is sensitive operational metadata, and DEBUG is not authorization. This is not available in non-debug mode and must not be pointed at a real or valuable database.

## Evidence and limits

Synthetic PostgreSQL tests check one-statement behavior in a read-only transaction, bound malicious-looking names, missing and non-table relations, role attributes against PostgreSQL, output/error gates, an absent `public` schema, and RLS flags. A temporary restricted role is granted SELECT on one synthetic table; a role switch changes the observed current attributes and selected table-level privileges while the superuser session role remains visible. A separate column-only grant permits a SELECT while the reported table-level SELECT count remains zero. Another test shows a superuser still reads a table with enabled and forced RLS. A non-superuser synthetic table owner sees rows under enabled but unforced RLS despite no policies; forcing RLS denies those rows in that selected case. Synthetic role/schema/DDL changes are transactionally rolled back. These are selected examples, not a security audit or a proof across PostgreSQL versions, role configurations or races.

Attribute flags apply only to the **current and session roles**, not a full account or possible `SET ROLE` membership/privilege graph. A disposable-superuser test grants an unprivileged synthetic role membership in a synthetic superuser role: the initial report shows neither role as superuser, but switching roles succeeds and exposes superuser privileges. Session authorization can itself change; the displayed session role is not necessarily the original login identity. A separate test changes session authorization to an unprivileged synthetic role and observes both flags become false; this does not prove the connection was originally unprivileged. A switched or inherited role, default privileges, ownership, functions, column-level grants, sequences, views, temporary schemas, security-definer code, role changes and privileges on nonselected tables may matter. Table-level privilege checks do not establish that rows are accessible: schema USAGE, RLS policies, current session mode and other checks also apply. Conversely a zero table-level count does not exclude column access. RLS catalog flags do not inspect policies or guarantee enforcement; superusers/BYPASSRLS can bypass them, and table owners generally bypass unforced RLS. Read-only is the current transaction setting, not a guarantee about other transactions or operations. A TLS result concerns only the connection observed by this PostgreSQL server, not the whole client/proxy path or certificate validation; a Unix socket or lack of TLS is not inherently a production-security conclusion. Missing relations can undercount grants. This does not verify backup, isolation, authenticity, source rights, deployment policy or production readiness.
