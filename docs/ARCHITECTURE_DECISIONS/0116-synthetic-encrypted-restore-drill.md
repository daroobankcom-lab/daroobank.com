# ADR 0116: synthetic encrypted-envelope restore drill

Status: opt-in development test, 24 November 2026. This is not a production backup implementation, encryption policy or key-management design.

## Decision and evidence

An isolated PostgreSQL test optionally creates an ephemeral self-signed certificate and **unencrypted synthetic private key**, dumps synthetic cross-domain data, and uses the local OpenSSL CMS utility to wrap the archive with AES-256-GCM. It checks the envelope is reported as CMS AuthEnvelopedData with AES-256-GCM, rejects one modified envelope and one wrong recipient key, and restores the successfully decrypted archive to a fresh synthetic target. A separate ORM process checks selected cross-domain relationships and migration state. The test uses a mode-0700 temporary directory and precreated mode-0600 files; the raw dump, private key, decrypted archive and failed-decryption output are still plaintext on local storage. CI explicitly opts into the exercise with PostgreSQL 16 clients and the runner's OpenSSL; it is otherwise skipped.

The test never feeds rejected output to `pg_restore`. OpenSSL may write plaintext before reporting an authentication failure: one local OpenSSL 3.0.20 probe returned failure on a modified synthetic envelope while leaving 24 bytes in its output file. A failed output must not be treated as authenticated merely because it exists. Behavior may vary by version; deletion on normal temporary-directory cleanup is not guaranteed secure erasure.

As a negative control, a second, different synthetically generated valid PostgreSQL archive is encrypted using only the same public certificate. Decryption and archive listing succeed: an authenticated-encryption envelope detects some changes to a given ciphertext, but does **not** authenticate the backup creator or prevent replacement by someone able to encrypt to that public certificate. The second archive is not restored by the test.

The exercise also signs the first ciphertext with a separate ephemeral RSA-PSS/SHA-256 test key and verifies its detached signature before the successful decryption. The selected modified ciphertext, a wrong public key and the replacement envelope fail that signature check. Rechecking the original pair succeeds, demonstrating that signature verification alone does not prevent replay. In this test the signing key and public verification key are generated and held alongside the archive; real trust requires independently authenticated key distribution, operational controls and freshness/retention policy.

## Limits

All input, certificates and keys are synthetic, generated on the same machine and used once. The private key is unencrypted and is not backed up or protected by a key manager. The synthetic detached signature does not provide trusted key distribution, anti-replay, certificate validation, key rotation or operational separation of duties. There is no off-host storage, retention, monitoring, backup scheduler, point-in-time recovery or production credential handling. Selected tampering and wrong-key cases do not prove cryptographic correctness, all failure modes, data completeness or availability. A crash can leave plaintext files or databases; random names and settings guards do not prove a safe server. Use only a separately authorized disposable cluster and synthetic data; independently design and review actual backup, signing, encryption and key-recovery policy before deployment.
