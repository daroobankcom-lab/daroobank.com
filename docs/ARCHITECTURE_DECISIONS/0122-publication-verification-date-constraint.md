# ADR 0122: require a verification date for the published flag at database level

Status: development migration, 24 November 2026. Not a publication approval or production migration plan.

## Decision

`catalog.ProductPresentation` already rejects `published=True` with a missing `verified_at` in model validation, and public reads withhold such rows. Migration `catalog.0008` adds a PostgreSQL check constraint for exactly this invariant: `NOT published OR verified_at IS NOT NULL`. It prevents selected bulk/direct SQL paths from creating that invalid combination even when model validation is bypassed. The constraint does not make the timestamp, source, rights, record or publication clinically valid; it allows unpublished records with or without dates and published records with any non-null date. Other malformed fields remain possible, and read-side validation still matters if a constraint is removed or bypassed.

## Existing databases and locking

Adding a validated CHECK can take a table lock and scan existing rows. If even one existing row has `published=true` and `verified_at IS NULL`, migration fails rather than changing data or fabricating verification dates. PostgreSQL rolled back the failed migration in the selected synthetic test. Do not apply this migration to a real system without explicit authorization, a tested backup and restore plan, inventory/review of invalid records, lock/availability planning and a separately reviewed remediation decision. For an authorized operator, a read-only count of that exact invalid combination can be a preliminary clue, not a consistent deployment guarantee: `SELECT count(*) FROM catalog_productpresentation WHERE published AND verified_at IS NULL;`. Concurrent writes, permissions, schema drift, other invalid data and failure logs remain concerns. Never blindly unpublish, delete or assign a date to real records.

## Synthetic evidence and limitations

PostgreSQL tests verify selected invalid `QuerySet.update`, SQL and `bulk_create` paths fail with `23514`, while the three valid flag/date combinations work. A historical migration test preserves valid records and demonstrates one invalid legacy row causes migration failure without a recorded migration, constraint or data rewrite; its fixture is then corrected solely inside the disposable test database so the graph can be restored. A two-connection probe shows an existing reader can block the DDL until `lock_timeout` (`55P03`), after which a retry succeeds. A setup-failure probe checks restoration after an invalid synthetic fixture was inserted. These samples do not cover all concurrency, data, failures, locks or database versions.

Three pre-existing defensive read/partial-save/repair tests temporarily remove this one constraint inside an isolated test transaction to continue exercising corrupt or missing-schema cases; a test verifies selected isolation guards and rollback restore the constraint. Such name/setting checks are not proof of server identity. The older projection-migration fixture now uses a date for published rows so its cleanup can restore the new graph; the separate migration test preserves coverage of a legacy invalid row. Interrupted tests, cleanup failures, direct schema changes, disabled constraints, superuser access and real-world migrations remain outside these guarantees. Use only an authorized disposable cluster and synthetic data.
