# ADR 0181: opt-in synthetic staff-login throttle

Status: development-only defense-in-depth experiment; not MFA, a production login policy or a security assessment.

## Decision

With both `DAROOBANK_DEBUG=1` and the exact opt-in `DAROOBANK_STAFF_LOGIN_THROTTLE=1`, CSRF-accepted POSTs to `/staff/login/` consume a shared PostgreSQL fixed-window quota before authentication: ten attempts per server-provided `REMOTE_ADDR` per 60-second window, then generic 429 responses until that window ends. Both successful and unsuccessful submissions count and success does not reset the window or revoke an existing session. GET/HEAD and CSRF-rejected POSTs do not consume a quota. Unknown/malformed addresses and selected database failures return a generic 503 without authentication. The existing staff portal remains disabled outside debug, and this option also evaluates false outside debug.

The database stores a keyed SHA-256 HMAC of the canonical IP (including normalization of IPv4-mapped IPv6), start time and a saturated attempt counter; it stores no raw address, username or password. Addresses come only from `REMOTE_ADDR`, never `X-Forwarded-For`. A short PostgreSQL transaction takes a row lock via an upsert, obtains the database clock after the lock, and serializes the increment across participating workers. A backward clock fails closed. One-second lock and two-second statement timeouts bound selected server-side waits; connection/network and whole-request times are not bounded. To avoid leaking timeout state or holding the lock in an enclosing transaction, calls in an outer or non-autocommit transaction fail closed.

The fixed window can allow bursts across a boundary; it does not defend against distributed guessing, account takeover by other routes, credentials already compromised, direct service calls or nonparticipating writers. Behind a reverse proxy, many clients may share the proxy's address and deny one another; untrusted forwarding headers are intentionally ignored. Correct server/proxy client-address configuration, network access restrictions and protection of `SECRET_KEY` remain essential. Rotating the secret changes keys and resets this limiter. Quota exhaustion does not reveal whether an account exists, but other response timing and operational logs can still leak information. No attempt is made to prove anonymity: hashes are pseudonymous and become linkable/guessable if the secret is compromised.

There is no scheduler or hard bound on the number of unique IP rows. To avoid indefinite storage in synthetic development, `python manage.py cleanup_staff_login_windows` performs a read-only dry run by default; `--apply` deletes at most 500 windows older than 24 hours according to the database clock. It returns aggregate counts, not keys. The selected delete rechecks age after a concurrent row-lock wait. The row-count limit does not bound database scanning, sorting or lock waits. Repeated authorized runs and independent access controls are required; absent a scheduler rows can accumulate and abuse can exhaust resources. The DEBUG gate is not proof of isolation or authorization. Never run it against real or production data.

## Evidence

Synthetic tests cover opt-in/configuration, generic CSRF-protected HTTP outcomes, no authentication when blocked, success and failure counting, IPv4-mapped addresses, ignored forwarded headers, missing addresses, no sensitive response text, session preservation, real lock timeout and connection reuse, and concurrent consumers. The cleanup tests cover dry-run, caps, age, debug gate and one coordinated refreshed-row race. These selected schedules do not prove universal concurrency, secure deployment, suitable thresholds or resilient abuse prevention.
