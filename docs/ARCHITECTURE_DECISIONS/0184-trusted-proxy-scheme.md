# ADR 0184: opt-in trusted proxy scheme handling

Status: configuration foundation only; no proxy, firewall, TLS endpoint or deployment is provisioned or approved.

Django normally treats `X-Forwarded-Proto` as untrusted unless configured otherwise. For a non-debug deployment behind a reviewed TLS-terminating proxy, `DAROOBANK_TRUST_PROXY_SSL_HEADER=1` opts in and requires `DAROOBANK_TRUSTED_PROXY_CIDRS`: one to 32 explicit IPs/CIDRs, syntactically strict, with no universal IPv4 or IPv6 coverage even through a combined list. Absent or malformed configuration fails startup when opted in. The flag is ignored in debug and is off by default.

An early middleware, before Django's security and CSRF middleware, removes `X-Forwarded-Proto` unless the immediate `REMOTE_ADDR` is in a configured network and the value is exactly the single lowercase token `http` or `https`. IPv4-mapped IPv6 peers are compared as IPv4; configure their IPv4 networks. Comma-separated or malformed values are discarded rather than taking a potentially attacker-supplied first value. Untrusted forwarded values cannot change Django's view of a direct HTTPS request. Forwarded host is not enabled; the proxy must pass the intended `Host`, and Django still validates it against the explicit host allowlist.

These checks are not peer authentication. A broad network may include untrusted machines even though it is not universal, a local process can connect from loopback, and `REMOTE_ADDR` may already have been rewritten by another component. A trusted proxy that forwards rather than overwrites a client-supplied single `X-Forwarded-Proto: https` can still enable spoofing. Before any real deployment, independently firewall the application so only authorized proxies reach it, use the narrowest verified network list, ensure every proxy replaces inbound forwarding headers, preserve the approved Host, validate TLS and origin behavior end-to-end, and review direct/alternate paths. The optional synthetic login limiter still keys by the server's `REMOTE_ADDR`, so users behind a proxy may share a limit; this feature does not change that behavior.

This does not configure HSTS, certificates, proxy trust for client IPs or hosts, monitoring, session security policy, production hardening or legal/clinical authorization. TLS topology and owners remain unresolved. Synthetic tests cover default-off and invalid network settings, complementary universal ranges, direct and forged peers, single/comma-separated protocol values, mapped IPv4, unchanged direct HTTPS, secure cookies and selected CSRF origin/referer behavior. They do not prove the behavior of an actual deployment or intermediary chain.
