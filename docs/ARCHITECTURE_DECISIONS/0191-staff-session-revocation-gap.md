# ADR 0191: known staff-session revocation gap

Status: **the revival scenario named below is closed by [ADR 0213](0213-durable-session-invalidation.md)**; the residual gaps listed there remain open, and the rest of this record is unchanged observation rather than a revocation implementation.

Superseded in part (2026-11-26): a session is now bound at login to a digest of the account state and `StaffSessionGuardMiddleware` flushes it on any difference, read from the account the session names rather than from `request.user`. Deactivation, staff-flag removal, permission and group changes, account deletion and password changes therefore end the session and its row, and restoring the state does not revive it; the two tests that used to demonstrate the gap now assert the opposite. Still open here: a transition no request observes (which is what the `revoke_staff_sessions` command is for), in-flight requests that already passed the guard, backend removal from settings, MFA, replay protection, session inventory and any production procedure.

The development staff portal uses Django's default database-backed sessions and authentication backend. Selected synthetic tests show that an existing session is denied staff access while the user's `is_staff` flag is false, and a deactivated user is redirected to login. However, if the account is reactivated or the staff flag is restored before the session expires, the same previously established session can again access the development workspace. Observing a denial while a flag is off is therefore **not durable session revocation**.

In a selected synthetic test, changing the password through Django before reactivation makes the old session fail the session-auth-hash check on its next request. This is evidence of Django's behavior in that scenario, not a complete revocation or incident procedure: an already-running request, alternate backends, other credentials, direct writes, reauthentication, session storage, recovery and operational races are outside its scope. There is no account lifecycle UI, centralized session inventory, bulk revocation service or durable per-account session generation in this project.

A further synchronized synthetic PostgreSQL test pauses one authenticated workspace GET after its authorization checks, disables the account and changes its password to an unusable value, then resumes the request. That in-flight read returns 200 even though the update committed before the response. A later request after reactivation is redirected because its session hash no longer matches. Another selected test exercises two independent old sessions and an unrelated account. An earlier synchronized HTTP POST with a valid CSRF token also showed a synthetic source claim being committed after account disable and password invalidation. The selected source-claim write now serializes its account status check and write with changes to that account row; see [ADR 0192](0192-source-claim-account-status-serialization.md). That limited mitigation does not cover other writes, durable session revocation or permission changes, and cannot cancel a writer that acquired the lock first. These observations are specific to the default backend, database sessions and selected routes; they do not characterize every write path or define a safe account-disable procedure. Resetting a password is disruptive and does not cancel requests that have already passed their checks.

Before production, choose and independently review an account/session lifecycle design that invalidates existing credentials and sessions when access is removed, including off/on transitions between requests, multiple workers, concurrent logins and in-flight requests. Define authenticated administrative actions, audit, recovery, key rotation, affected session stores and tests for direct/bulk changes or explicitly prohibit them with enforceable controls. Combine this with the proposed MFA and incident-response work; neither this record nor a password-change test authorizes production or real users.
