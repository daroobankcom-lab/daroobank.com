# Deployment

A development Django application, PostgreSQL-only configuration, `.env.example` and a development Compose stack exist; there is no production deployment configuration or infrastructure. The Compose stack and development server are not suitable for production. No deployment has been performed or authorized.

## Non-debug configuration prerequisites

Non-debug startup requires an explicit `DAROOBANK_SECRET_KEY` and `DAROOBANK_ALLOWED_HOSTS`. The key must meet the shape checks in [ADR 0183](ARCHITECTURE_DECISIONS/0183-nondebug-config-guards.md); those checks cannot establish randomness or secrecy. Supply a unique randomly generated key through an approved secret manager. List only authorized ASCII hostnames (IDNA/punycode for international names) or bracketed IPv6 addresses, without ports or URLs; `*` is refused and `.example.org` trusts all of its subdomains. Changing a key affects existing signatures and sessions; no production rotation policy is implemented. These requirements do not configure a production deployment or grant authorization.

## Optional HSTS header

HSTS is off unless `DAROOBANK_HSTS_SECONDS` is explicitly set to a positive value outside debug. Before using it, review HTTPS certificates, proxy behavior, affected hosts and recovery: browsers cache this policy, and later setting the option to zero does not clear an existing browser policy. The application does not enable subdomain inclusion or preload; an upstream proxy may independently set HSTS. See [ADR 0185](ARCHITECTURE_DECISIONS/0185-opt-in-hsts.md).

## Optional proxy scheme configuration

For a separately reviewed non-debug TLS proxy only, `DAROOBANK_TRUST_PROXY_SSL_HEADER=1` requires an explicit `DAROOBANK_TRUSTED_PROXY_CIDRS` list. The application accepts only a single `http` or `https` value from an immediate peer in those networks. This is **not** a firewall or proof that the peer is an authorized proxy: the proxy must overwrite incoming forwarding headers, preserve the approved Host, and the app must be network-restricted. The flag is off by default and ignored in debug. Do not enable it until the complete topology is reviewed and tested; see [ADR 0184](ARCHITECTURE_DECISIONS/0184-trusted-proxy-scheme.md).

## Optional minimal operational probes

`DAROOBANK_HEALTH_PROBES_ENABLED=1` opts in to unauthenticated `/health/live/` and `/health/ready/` GET/HEAD paths; the default is off. Liveness only checks that the process can return a response, while readiness performs a narrow default PostgreSQL `SELECT 1`, not a complete service or migration check. A failure returns 503 without database details. Network/proxy restrictions, polling limits, host and HTTPS configuration, response deadlines, monitoring and incident ownership remain external responsibilities. A PostgreSQL statement timeout is not a hard request deadline. See [ADR 0180](ARCHITECTURE_DECISIONS/0180-opt-in-process-database-probes.md); enabling these paths is not production authorization. For the wider settings and migration shape, `manage.py check_deployment_readiness` reports ten required checks and the conditions that still need a decision in one JSON document; it is not monitoring, serves no request and does not replace these probes ([ADR 0217](ARCHITECTURE_DECISIONS/0217-deployment-readiness-report.md)).

## Configuration reference

Every environment variable the application reads, where it is enforced, and what a non-debug deployment is expected to set. `.env.example` is a development template and `compose.yaml` is a development stack; neither is a production configuration. `daroobank/test_environment_documentation.py` holds this table to the code, so a new variable is a documented event ([ADR 0222](ARCHITECTURE_DECISIONS/0222-documented-environment.md)).

| Variable | Required | Expected in a non-debug deployment | Enforced by |
|---|---|---|---|
| `DAROOBANK_DEBUG` | no; off unless it is exactly `1` | must stay unset or `0`. `1` enables diagnostic pages, relaxes the host and secret guards, disables HSTS and exposes the staff portal, so a production process must never set it | `settings.py`; the readiness check `debug_disabled` ([ADR 0217](ARCHITECTURE_DECISIONS/0217-deployment-readiness-report.md)) |
| `DAROOBANK_SECRET_KEY` | yes outside debug | a unique randomly generated value from an approved secret manager, never in Git or shell history. In debug an empty value falls back to a fixed development string | `require_nondebug_secret`, [ADR 0183](ARCHITECTURE_DECISIONS/0183-nondebug-config-guards.md) |
| `DAROOBANK_ALLOWED_HOSTS` | yes outside debug | an explicit comma-separated list of authorized ASCII hostnames or bracketed IPv6 addresses, without ports or URLs; `*` is refused | `require_nondebug_hosts`, [ADR 0183](ARCHITECTURE_DECISIONS/0183-nondebug-config-guards.md) |
| `DAROOBANK_HSTS_SECONDS` | no; ignored in debug | a positive integer of seconds, `0` through `31536000`, only after TLS, proxy and rollback review; browsers cache the policy | `parse_hsts_seconds`, [ADR 0185](ARCHITECTURE_DECISIONS/0185-opt-in-hsts.md) |
| `DAROOBANK_TRUST_PROXY_SSL_HEADER` | no; ignored in debug | `1` only behind a separately reviewed TLS proxy that overwrites incoming forwarding headers | [ADR 0184](ARCHITECTURE_DECISIONS/0184-trusted-proxy-scheme.md) |
| `DAROOBANK_TRUSTED_PROXY_CIDRS` | yes when the flag above is `1` | an explicit list of immediate-peer networks; the flag is refused without it | `require_trusted_proxy_networks`, [ADR 0184](ARCHITECTURE_DECISIONS/0184-trusted-proxy-scheme.md) |
| `DAROOBANK_HEALTH_PROBES_ENABLED` | no; off unless `1` | `1` only where `/health/live/` and `/health/ready/` are network-restricted, since they are unauthenticated | [ADR 0180](ARCHITECTURE_DECISIONS/0180-opt-in-process-database-probes.md) |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_HOST` | yes | explicit values; the process refuses to start without each of them, and no default is invented | `required_database_setting` in `settings.py` |
| `POSTGRES_PASSWORD` | yes for password authentication | from a secret manager; an empty value is accepted only where the server authenticates another way, which is not a reviewed production setup | `settings.py` |
| `POSTGRES_PORT` | no; `5432` | an integer port | `settings.py` |
| `POSTGRES_SSLMODE` | no; the driver default | `verify-full` for any connection that leaves the host, so the server certificate is checked and the link is encrypted in transit; unset means the driver decides | `settings.py` `OPTIONS` |
| `POSTGRES_CONN_MAX_AGE` | no; `0` | integer seconds. Persistent connections need pooling, failover and idle-timeout review before they are used in production | `settings.py` |
| `DAROOBANK_STAFF_LOGIN_THROTTLE` | development only | ignored unless debug is on, and not a production abuse control; window rows need maintenance ([development guide](DEVELOPMENT_GUIDE.md#development-only-staff-login-throttle-and-window-cleanup), [ADR 0181](ARCHITECTURE_DECISIONS/0181-development-staff-login-throttle.md)) | `settings.py` |

`DJANGO_SETTINGS_MODULE` is the one variable the project only ever defaults, in `manage.py`, `daroobank/wsgi.py` and `tools/wait_for_database.py`; a deployment sets it explicitly to `daroobank.settings`.

## Abuse protection is external

The application itself has **no rate limit** on any public route, and no request size ceiling beyond what a form checks after the body has arrived. Both have to be provisioned by the reverse proxy, a CDN or the host before this service faces the public internet; nothing in this repository arranges them, and no configuration variable turns them on.

Measured by `daroobank/test_no_abuse_protection.py` ([ADR 0223](ARCHITECTURE_DECISIONS/0223-no-abuse-protection.md)):

- Repeated anonymous reads — eight in a row of the home page, the about page, the price list, the search page, the search API and the OpenAPI document — all answer 200 with no `Retry-After`, no `X-RateLimit-*` header and no row written anywhere.
- The only limiter in the project is the opt-in, debug-only staff login window ([ADR 0181](ARCHITECTURE_DECISIONS/0181-development-staff-login-throttle.md)): one call site, ten attempts per client key in a rolling minute, answering 429 with no `Retry-After` header when limited and 503 when the limiter itself is unavailable. It protects one form in one debug-only portal; it is not a platform control and it is off in production configuration.
- `DATA_UPLOAD_MAX_MEMORY_SIZE` and `FILE_UPLOAD_MAX_MEMORY_SIZE` are left at Django's defaults (2.5 MiB each) and `settings.py` sets neither; the first bounds a non-file request body, the second only decides whether an upload spools to memory or to a temporary file. No module answers 413.
- The upload limits that do exist are per-form `upload.size` checks — 1 MiB for product intake, 2 MiB for price staging — so they run after Django has received and spooled the body, and an oversized upload is refused with the form's own validation error, not with a transport-level status.

Provision therefore, at the edge: request-rate limiting per client and per route, a request-size and upload-size limit that refuses before the body is buffered, connection and slow-client timeouts, and volumetric absorption. Review those limits against the bounded page sizes and the 2 MiB CSV validation limit so a legitimate upload is not refused by the proxy or accepted by the proxy and refused later by the form. Until they exist, treat any public exposure of this service — including a reachable development preview — as unprotected against scraping and volumetric abuse.

## Proposed deployment topology

TLS-terminating reverse proxy → independent Django web processes → PostgreSQL; separate scheduler and bounded worker processes → Redis queue and permitted source endpoints. Use private networks and least-privilege credentials; optionally private object storage for authorized payloads/images. Isolate worker resource quotas and egress so a crawl failure does not take down the web service. Choose provider/region only after review of Iranian connectivity, resilience, sanctions/vendor constraints, data residency and qualified local legal advice.

## Release gates

- Pin and scan dependencies and base images, generate SBOM where practical, run tests/migrations on staging and validate rollback compatibility. Measured today: the Python half is exact (both lock files hash-pinned, `--require-hashes` on every install, a negative control that requires pip to reject a wrong hash, the runtime lock verified first, `pip-audit --strict` against the lock and the built image) and the artifact half is absent — CI uploads nothing, pushes no image, generates no SBOM, signs nothing, pins no base image by digest (`postgres:16` and `python:3.11-slim` are mutable tags), defines no staging environment and exports no value between steps, and the only buildable image is an untagged root-owned development image destroyed inside the run ([ADR 0226](ARCHITECTURE_DECISIONS/0226-ci-artifact-gate.md)). Encrypted secrets delivered by a secret manager; `.env.example` holds placeholders only when configuration is implemented.
- Provision TLS, secure headers, database backups and off-host encrypted retention, monitoring/alerts, access review and restore drills. Separate production from development and do not use patient data in non-production.
- Test proxy host/origin and cookies, health endpoints, database migrations, worker isolation and no internet dependency for web health. Production release requires explicit user authorization and clinical/data-source sign-off for published data.
- Run `python manage.py check_deployment_readiness` for each process before and after a deploy: it writes nothing, exits non-zero when a required check fails, and `--strict` also fails while any condition still needs a decision. A zero exit status is not a deployment authorization ([ADR 0217](ARCHITECTURE_DECISIONS/0217-deployment-readiness-report.md)).
- Use expand/contract migrations and versioned API; snapshot/backup before destructive change. Define rollback including content/cache and migration compatibility before release. Reverse proxy caching must respect private responses and invalidation. A measured rollback of this schema is not one command: the plan for `migrate catalog zero` is 11 migrations, is not ordered by app (`ingestion 0002` runs first) and commits each migration alone, so a block on any table it touches leaves the database half undone with rows already destroyed — one row held `FOR UPDATE` is enough, because dropping a child table takes `AccessExclusiveLock` on its parent. Set `lock_timeout`, stop the writers, copy the tables the cascade will drop before starting, and treat `setval` on the identity sequences as part of any restore ([ADR 0225](ARCHITECTURE_DECISIONS/0225-populated-rollback-drill.md)).

## Development CI and proposed CI/CD

A basic `.github/workflows/checks.yml` runs on pushes and pull requests with read-only repository contents permission and a temporary PostgreSQL service: pinned Python dependencies are installed, then connection wait, migrations, pip check, Django check, migration drift check and synthetic tests run against PostgreSQL. It does not deploy, upload backups or establish production readiness. Checkout, Python setup and Node setup actions are pinned to version-specific commit SHAs checked against official release tags; checkout does not persist repository credentials. These pins require periodic review and updates and do not verify upstream behavior or secure transitive downloads. Runtime Python and image bootstrap package artifacts are hash-locked as described in the [development guide](DEVELOPMENT_GUIDE.md#maintaining-python-dependency-locks); auditor dependencies and the initial image tooling are not. Base/service image tags remain mutable and the build is not reproducible or supply-chain complete. Hosted results depend on GitHub Actions being enabled.

The workflow also runs synthetic Chromium/axe checks, Compose persistence/build-context probes, and scoped PyPI/npm advisory scans described in [Testing strategy](TESTING_STRATEGY.md). These rely on external registries and do not scan OS packages or establish production security. Further proposed gates include comprehensive lint/type checks, security scanning, accessibility review and contract tests. On a separately authorized release: build immutable artifact, run staged smoke tests, require approval, deploy and observe. Those additional gates and release steps are plans, not implemented.
