# Development guide

## Current local implementation

Requires Python 3.11+ and PostgreSQL. Copy `.env.example` to `.env` and replace the placeholders with unique local values. The template holds every variable the application reads; [the deployment guide](DEPLOYMENT.md#configuration-reference) lists each one with its production expectation and what enforces it ([ADR 0222](ARCHITECTURE_DECISIONS/0222-documented-environment.md)). Never commit credentials: `.env` and `.env.*` files are ignored by Git except `.env.example`, and ignore rules do not remove already tracked files. Compose loads `.env` automatically:

```sh
docker compose up --build
```

The Docker build context excludes environment files other than `.env.example` templates, `.git`, `.venv`, `.cache`, `backups`, `node_modules` and dump/backup files. Existing Compose environment injection is unchanged. Never put secrets or real data in example templates or other build-context paths; ignore rules are not a substitute for secret scanning or access control, and they do not remove files from existing images or Git history. CI checks these exclusions using synthetic files in an ephemeral checkout.

The development stack starts PostgreSQL 16 with a health check and persistent named volume. Django waits for a connection, applies migrations and starts the development server. Catalog migration `0008` adds a validated check that published presentations have a non-null verification date; it fails on existing violations and may wait for table locks. It does not repair or verify data. Review [ADR 0122](ARCHITECTURE_DECISIONS/0122-publication-verification-date-constraint.md) before applying it anywhere; never blindly modify existing records. The readiness helper's 60-second retry window prevents starting a later attempt after the deadline, but is not a hard timeout: an already-started connection, DNS lookup or query can overrun it; it neither cancels an operation nor verifies schema readiness. See [ADR 0076](ARCHITECTURE_DECISIONS/0076-postgresql-readiness-window.md). PostgreSQL is bound only to localhost on `POSTGRES_PORT`; Django inside Compose uses `db:5432`. Do not run multiple migration-starting web replicas or use this development stack as a production deployment. Measured on synthetic data: that constraint migration scans 200,000 rows in 0.100 s and writes 2,464 bytes of WAL, blocks no writer under a load of about 195 writes a second, and refuses a single violating row after 0.052 s without being recorded — a forward migration that fails leaves the schema as it was, while a rollback that is blocked leaves it half undone; no migration connection carries a `lock_timeout` here, and what one would change is priced in [the database migration plan](DATABASE_MIGRATION_PLAN.md) ([ADR 0233](ARCHITECTURE_DECISIONS/0233-database-migration-plan.md)). `docker compose down` preserves data; **`docker compose down -v` deletes the database volume**. Changing credentials in `.env` does not update an already-initialized PostgreSQL volume; manage roles/password rotation explicitly.

For Django outside Docker, provision a PostgreSQL database/role or start only the Compose `db` service. Export `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_HOST` (normally `127.0.0.1` for the mapped Compose port); `POSTGRES_PORT` defaults to 5432. Django does not load `.env` itself. To load a trusted shell-compatible `.env`, use `set -a; . ./.env; set +a`; never source untrusted files. `POSTGRES_PASSWORD` can be empty when an explicitly configured peer/certificate authentication method is used. `POSTGRES_SSLMODE` is passed to libpq when set; production must use an appropriate certificate-verified TLS configuration. `POSTGRES_CONN_MAX_AGE` defaults to zero and accepts integer seconds from 0 through 31,536,000; Django health-checks persistent connections when configured. Values above this bound now fail startup instead of creating an unsafe or unrepresentable connection deadline. This is a configuration compatibility change, not a recommendation to keep connections for a year.

The role a developer provisions this way is the cluster's superuser in every environment this repository defines, and that is measured rather than assumed: one non-system role owns all 33 tables, `POSTGRES_CONN_MAX_AGE` defaults to `0` so every request opens and closes a connection at about 2 ms, `db_options` carries only `connect_timeout: 5`, and a least-privilege role with `SELECT, INSERT, UPDATE, DELETE` cannot run migrations without `CREATE` on the schema, cannot create an index or `TRUNCATE`, cannot create the test database the runner needs, and reports success from a `VACUUM` that does nothing ([the database connection plan](DATABASE_CONNECTION_PLAN.md), [ADR 0236](ARCHITECTURE_DECISIONS/0236-database-connection-plan.md)).

```sh
python3 -m venv .venv
.venv/bin/python -m tools.verify_runtime_lock
.venv/bin/pip install --require-hashes -r requirements.txt
export DAROOBANK_DEBUG=1
.venv/bin/python -m tools.wait_for_database
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver 127.0.0.1:8000
.venv/bin/python manage.py test --settings=daroobank.synthetic_test_settings --noinput
.venv/bin/python manage.py makemigrations --check --dry-run
```

### Maintaining Python dependency locks

`requirements.in` records the direct exact runtime pins; `requirements.txt` additionally pins transitive dependencies and SHA-256 hashes of published PyPI release artifacts. Do not install `requirements.in` alongside the lock: pip requires hashes on every requirement in hash-checking mode. The image separately uses `requirements-build.txt` for its pip/setuptools upgrade. CI checks direct pins against the runtime lock, but that small checker is not a dependency resolver and does not verify artifact hashes; pip does that during installation.

To update, review the direct and transitive versions and their dependency metadata, update `requirements.in` and the lock together, obtain and independently review hashes of the intended distribution artifacts from a trusted source, and run the lock check, a clean `pip install --require-hashes -r requirements.txt`, `pip check`, advisory scans and the full tests/CI. Review platform markers and compatible wheels for each target environment. The lock includes source distributions and multiple platforms' artifacts; builds from source have additional build-dependency risks. Docker's base Python/initial pip and the audit tool's dependencies are not covered by these locks. Hashes only verify bytes against the checked-in values; they do not establish publisher identity, provenance or safety. This is not a fully reproducible build.

As an optional maintenance aid, `python -m tools.check_lock_metadata` compares both lock files' hash sets against the current PyPI release JSON for every listed version, including conditional packages, source distributions and yanked files. It needs network access to PyPI, makes no file changes or artifact downloads, and returns nonzero for a mismatch, unsupported lock syntax or registry failure. It reports both extra and missing hashes: a deliberate subset of release artifacts also reports a mismatch, as can later upstream additions or removals. Review the specific artifacts and release changes before updating a lock; do not copy new hashes blindly. The tool relies on PyPI's current metadata and TLS, not an independent trust root; it neither verifies downloaded bytes nor resolves dependencies, evaluates markers, confirms availability/compatibility, checks signatures or proves safety. Pip's hash-checked clean installation and other review remain necessary.

The Django test runner creates and destroys a separate `test_` database; the configured role needs CREATEDB permission. The isolated synthetic, browser and restore settings assign a random name per invocation and reject `--keepdb` and Django `--parallel`. Their PostgreSQL test-creation backend makes one CREATE attempt and refuses an existing name without deleting or reusing it, including with `--noinput`; direct cloning is also refused. Teardown accepts only the name that the same creation instance recorded after successful CREATE and consumes that record before one DROP attempt. A recorded name is not an identity or ownership proof. This does not prevent name collisions, protect against replacement before or during teardown, isolate shared resources, or automatically remove databases after a crash or failed DROP. Other settings/backends and direct SQL bypass this guard; the ordinary default test settings still use a predictable shared name and can delete an existing database on collision. Do not point any test runner at a production or valuable server. Tests and local data must be synthetic; see [ADR 0071](ARCHITECTURE_DECISIONS/0071-isolated-general-tests.md), [ADR 0109](ARCHITECTURE_DECISIONS/0109-isolated-test-database-collision.md) and [ADR 0114](ARCHITECTURE_DECISIONS/0114-isolated-teardown-name-guard.md). `DAROOBANK_SECRET_KEY` is required when debug is off; host names are supplied by `DAROOBANK_ALLOWED_HOSTS`. In debug an empty value falls back to a published development constant that the non-debug shape check rejects. Changing the key at all invalidates every stored session, every signed cursor and both address-keyed limiter windows, and no command in this repository rotates it ([the secret-rotation plan](SECRET_ROTATION_PLAN.md), [ADR 0231](ARCHITECTURE_DECISIONS/0231-secret-rotation-plan.md)). Development preview accepts `.e2b.app`; production deployment is not configured or authorized.

## Actual layout

- `daroobank/`: Django settings, URL configuration and WSGI entrypoint.
- `catalog/`: narrow presentation model, public search and detail, and development-only private product candidate intake/review.
- `pricing/`: local CSV candidate staging, inspection and preliminary independent review; no public prices or network crawler.
- `sources/`: development-only source-rights assertion and preliminary review ledger, not an authorization gate.
- `ingestion/`: offline time-window inspection and development-only web intake receipts; no scheduler, source worker or network adapter.
- `clinical/`: private synthetic statement drafts, reference assertions and preliminary triage; no clinical approval or public content.
- `templates/`, `static/`: server-rendered Persian pages, shared tokens and locally hosted OFL-licensed Vazirmatn font.
- `docs/`: product, decisions, source research and operational plans.

In debug mode, an active staff account lands at `/staff/` by default after login and can use its read-only directory of sections allowed by existing view permissions. An explicitly requested safe `next` destination still takes precedence and the destination independently checks access; private staff pages link back to the directory. An account with no section permissions sees an empty directory. Four permitted queues provide shortcuts to their existing `pending` filter: it means no review event exists, not that an item is valid, reviewable by the current account, approved, or the only outstanding work. Deferred, rejected and referred records have review events and are not included. No counts, metrics or operational status are shown; this is not a production dashboard. Use synthetic accounts and data only.

The current schema and publication flag are not a complete provenance, review, audit or price workflow. There is no public editing interface. Database writes must not be used to bypass clinical and source-rights gates. Never add real credentials, private data or unlicensed source payloads to Git. More domains, independent workers and administrative approvals remain planned; see [architecture](SYSTEM_ARCHITECTURE.md).

## Local price-candidate staging

This local operator-only tool reads an explicitly authorized UTF-8 CSV; it does not download data, publish prices, approve products or alter catalog records. The included price CSV is **synthetic** and must never be treated as Iranian market data. After migrations, try a dry run:

```sh
DAROOBANK_DEBUG=1 .venv/bin/python manage.py stage_price_csv \
  examples/price_candidates.synthetic.csv \
  --source-name 'Synthetic example only' --source-url https://example.org
```

To store an authorized file for later review, supply `--commit --attest-authorized` only when the operator has confirmed that collection and internal storage are permitted. This flag is an operator assertion, not proof of a licence and not an audit trail. Staging from the command line also records **no account**: `PriceCandidate.staged_by` stays empty, and because an identical payload reuses the existing row, such a candidate never acquires an actor later and the staff portal cannot review it (its detail page shows no stager and offers no review form). It also writes **no import receipt and no receipt items**, so a command-line staging appears in no import inventory at `/staff/operations/imports/`, has no manifest and no per-row outcome record, while the same CSV through the web route writes a receipt naming the operator plus one item per row; and unlike the staff portal, the projection repair and the login throttle, the command is not gated on debug mode. Use `/staff/prices/import/` when a row has to be reviewable or an import has to be inventoried. The options for closing both gaps, with a counted price each, are written down in [the attribution gap plan](ATTRIBUTION_GAP_PLAN.md) — a proposal with no owner — and measured by `daroobank/test_attribution_gap_plan.py`. See [ADR 0220](ARCHITECTURE_DECISIONS/0220-actor-attribution-inventory.md) and [ADR 0229](ARCHITECTURE_DECISIONS/0229-attribution-gap-plan.md). Never put actual source files, patient information, credentials or private URLs into Git. `--source-url` must be HTTPS and cannot contain credentials, query parameters or a fragment. Local database and CLI commands are not protected by the web login; restrict access at the operating-system level. The web interface also supports staging with a separate permission and records the authenticated operator. CLI-created or older candidates lack an authenticated stager and cannot be reviewed through the web interface; replays do not change existing provenance. Active superuser bypasses, single-user permission accumulation, revision-lineage SoD gaps, unlocked `recheck_actor` races, the 5,000-row session scan cap and the 6 non-debug CLI commands are measured in [the API and permissions plan](API_PERMISSIONS_PLAN.md) ([ADR 0235](ARCHITECTURE_DECISIONS/0235-api-permissions-plan.md)).

CSV must contain exactly these column names, once each (order is flexible):

```text
source_record_id,irc,manufacturer,strength,dosage_form,package_description,amount,currency,category,unit,effective_date,source_published_date
```

The last two dates may be blank; otherwise use Gregorian `YYYY-MM-DD`. Currency must be explicitly `RIAL` or `TOMAN`; accepted categories are `official_consumer`, `retail`, `manufacturer`, `wholesale`, `unit`. Accepted units: `package`, `tablet`, `capsule`, `ampoule`, `vial`, `ml`; `unit` category cannot use `package`. Amounts must be positive plain decimals, and conversion must result in a whole Rial without rounding. The direct conversion helper also enforces the existing 50-character input limit, including when called outside CSV parsing. Unicode normalization can expand input and accepts some compatibility digits; controls, format characters, combining marks and line separators are rejected before they can be stripped from an amount. Legacy candidates containing them can fail integrity review. Conversion uses exact digit-string arithmetic; this is not price or source verification. See [ADR 0108](ARCHITECTURE_DECISIONS/0108-price-conversion-input-bound.md) and [ADR 0117](ARCHITECTURE_DECISIONS/0117-price-amount-invisible-characters.md). Direct Python callers of either intake service must pass an actual boolean for `commit` (default `False`); non-booleans are rejected before file reads or writes, and `True` requires explicit rights attestation. Programmatic callers of the synthetic projection-repair command must likewise supply boolean commit/confirmation options. See [ADR 0119](ARCHITECTURE_DECISIONS/0119-explicit-intake-commit-mode.md). The source's original value is retained after the documented cell trimming. Product and price CSV cells reject Unicode controls and surrogates before trimming; the two upload forms also check raw source fields. Selected source-claim, clinical and identity forms check raw single-line assertion fields too; unchanged empty component rows and multiline text follow their existing behavior. Ordinary outer spaces are still trimmed. See [ADR 0118](ARCHITECTURE_DECISIONS/0118-intake-raw-control-characters.md) and [ADR 0133](ARCHITECTURE_DECISIONS/0133-staff-form-raw-controls.md). The input is bounded to 2 MiB and 5,000 rows, and an invalid row aborts the whole file before writing.

To inspect locally staged candidates without changing their status:

```sh
DAROOBANK_DEBUG=1 .venv/bin/python manage.py list_price_candidates --limit 30
# Optional: --status suggested, ambiguous, or unmatched
```

During one preview or staging invocation, rows with identical normalized IRC, manufacturer, strength, dosage form and package description reuse the first matching observation for that identity. Different identities sharing an IRC also reuse an IRC candidate index while it remains in an eight-group per-call LRU; each group holds at most 100 presentations or an over-limit marker, and its query reads at most 101 rows. A matching identity result does not refresh IRC recency. After eviction a new identity may reload that IRC, while an already-seen identity still uses its first result. Other fields, including amount and source record ID, remain distinct row data and do not enter the match key; deduplication and row receipts are unchanged.

The per-identity cache holds at most 5,000 keys, but neither it nor the IRC cap bounds memory bytes, query work or time. Both caches are discarded after the invocation; the detail suggestion and accept-suggestion review check query afresh. Catalog changes may be missed, and even rows with the same IRC can reflect different times: this is not a snapshot or verification. A replay leaves the original candidate suggestion intact even when the new receipt records a different current invocation result. More than 100 indexed presentations still yields ambiguous for every identity, and unpublished presentations may still be suggested. A presentation whose matching text or displayed Persian name fails the narrow checks makes its normalized identity ambiguous; an unassignable non-string match field makes the IRC group ambiguous. Stale projections can still conceal candidates, and these checks do not verify identity. Existing stored suggestions and receipt outcomes are not rewritten. See [ADR 0020](ARCHITECTURE_DECISIONS/0020-price-staging-match-cache.md), [ADR 0021](ARCHITECTURE_DECISIONS/0021-price-irc-candidate-cache.md) and [ADR 0064](ARCHITECTURE_DECISIONS/0064-price-matching-unsafe-presentation.md).

For payloads passing the existing structural/derived consistency check, JSON includes `payload_status: consistent`, the original match status and a fresh current suggestion. For invalid payloads it outputs only the candidate ID, review-required flag, `payload_status: invalid` and an invalid current suggestion; it neither echoes their other fields nor attempts matching. Selected JSON above 65,536 characters in PostgreSQL's text representation is not transferred or classified: the reduced row instead has `payload_status: oversized` and current suggestion `match_status: unknown`. Consumers must handle both reduced row shapes. The limit counts all selected rows and `--status` filters the original stored status. This transfer cap does not bound database work, other fields or all commands. Consistency is not authenticity, confidentiality, review eligibility or source-rights verification; a coherent alteration can pass, and the source URL is not part of the price payload digest. Otherwise consistent output can still contain sensitive source text; restrict local output. See [ADR 0062](ARCHITECTURE_DECISIONS/0062-price-cli-payload-check.md) and [ADR 0170](ARCHITECTURE_DECISIONS/0170-bounded-price-cli-candidate-json.md).

The initial match is only a snapshot and can become stale; even a current exact match is **not verification**, does not establish IRC scope and must be independently reviewed. This command does not approve candidates. Existing candidate revisions are not changed on replay, and identical source/record/payload combinations are deduplicated. This command records no review decision. There is no tamper-proof audit log, official-source integration, automatic scheduler or public price publication.

## Development-only staff queue

After migrations, create an account **only in an isolated local development environment with synthetic data**:

```sh
DAROOBANK_DEBUG=1 .venv/bin/python manage.py createsuperuser
```

Django prompts interactively for the password; do not place passwords in shell commands, Git or chat. A superuser is broadly privileged and is for local testing only. No accounts or passwords are created automatically. For a less-privileged local viewer, give an existing active account `is_staff=True` and the Django permission `pricing.view_pricecandidate`, either directly or through a group; it does not need edit permissions. Grant/revoke permissions through controlled Django management tooling. Account provisioning and permission changes currently lack an audit workflow.

Start the server in debug mode and visit `/staff/login/`, then `/staff/prices/`. The queue and detail pages are bounded/paginated and accessible only to active staff with that view permission. The pages show the source assertion, original currency, converted Rial amount, and both initial and recalculated current match suggestions; neither suggestion is a review or approval. The match filter and summary counts use the **initial** match status; an independent review filter uses the latest recorded triage decision. Summary counts remain global regardless of filters. Logout is POST-only with CSRF protection. The app never shows candidate prices in public pages or API.

The staff portal is deliberately disabled when `DAROOBANK_DEBUG` is not `1`. This is not a production-ready staff system: MFA, production-grade login abuse protection (the opt-in development limiter described below is not one), hardened credentials, tamper-resistant audit, final approvals, retention policy, production deployment and security validation remain missing. The unowned [MFA implementation plan](MFA_IMPLEMENTATION_PLAN.md), measured in [ADR 0230](ARCHITECTURE_DECISIONS/0230-mfa-implementation-plan.md), prices six options for closing the MFA gap and implements none of them. Debug mode can expose diagnostic data and the developer preview can be publicly reachable: never use it with real credentials, sensitive data or real patient information. No source licence has been granted by this implementation.

## Development-only staff login throttle and window cleanup

`DAROOBANK_STAFF_LOGIN_THROTTLE=1` together with `DAROOBANK_DEBUG=1` enables an opt-in limiter on the staff login form: at most ten attempts per client key in a rolling sixty-second window, recorded in the `staff_security_staffloginwindow` table. It is a synthetic development control, is a no-op inside a test transaction, and is **not** a production abuse control — no proxy identity, alerting or independently reviewed policy sits behind it. See [ADR 0181](ARCHITECTURE_DECISIONS/0181-development-staff-login-throttle.md), [Security](SECURITY.md) and [ADR 0219](ARCHITECTURE_DECISIONS/0219-documented-command-surface.md), which holds this document to the command registry.

Enabled or not, window rows older than twenty-four hours are worth removing so the table does not grow without bound:

```sh
DAROOBANK_DEBUG=1 .venv/bin/python manage.py cleanup_staff_login_windows            # read-only: how many rows are eligible
DAROOBANK_DEBUG=1 .venv/bin/python manage.py cleanup_staff_login_windows --apply    # delete one bounded batch
```

Both forms print one JSON object and nothing else. The command refuses to run outside a debug environment, requires PostgreSQL in autocommit (it will not run inside an open transaction), sets a one-second lock timeout and a two-second statement timeout locally, and touches at most 500 rows per run, oldest first, rechecking a row's age after any lock wait so a freshly reset window is never deleted. Without `--apply` it reports `{"eligible": n, "more": bool, "mode": "dry_run"}`; with `--apply` it reports `{"deleted": n, "mode": "delete"}`. Repeat the run to clear more than one batch.

## Opt-in public read limit

`DAROOBANK_PUBLIC_READ_LIMIT=1` enables a fixed-window limit on public reads: at most 120 GETs per client key in a rolling sixty-second window, recorded in the `staff_security_publicreadwindow` table, after which a read is refused with 429, an empty body and a `Retry-After` delay. It works in debug and outside it, is off by default, and is not a substitute for the reverse-proxy rate limiting that `docs/DEPLOYMENT.md` requires. The key is an HMAC of the normalized `REMOTE_ADDR` under a scope of its own, so the table holds no address, path, query or account and cannot be joined with the login window. Staff paths and health probes are exempt, non-GET requests are not counted, and a limiter that cannot reach the database serves the read instead of refusing it. The local Compose stack passes the variable to the application service with a default of `0`, as it does the login throttle, so a value set only in an uncommitted `.env` still reaches the process.

Unlike the login window, no management command prunes these rows: `cleanup_staff_login_windows` handles only `staff_security_staffloginwindow`. Enable the read limit only where someone has decided how the table is maintained ([ADR 0228](ARCHITECTURE_DECISIONS/0228-public-read-limit.md)).

## Development-only staging and preliminary review

An active staff user needs both `pricing.view_pricecandidate` and `pricing.add_pricecandidate` to use `/staff/prices/import/`. Choose preview (no writes) or stage; staging requires an explicit attestation of permission for collection and internal storage. This is a self-assertion, not a licence check. Only validated structured fields are stored; the original file is not retained by the application. Django may temporarily buffer uploads during a request, and the 2 MiB validation limit is not a reverse-proxy request-size or malware-scanning control.

A different active staff user with both `pricing.view_pricecandidate` and `pricing.review_pricecandidate` can record a reasoned preliminary suggestion acceptance, rejection or deferral on the candidate page. A submitter cannot review their own candidate, including if they have all permissions. Acceptance requires a unique current exact suggestion and a matching product fingerprint; stale review versions and inconsistent stored payload/derived values are rejected. Rejection and deferral do not assert a product match. Events store the reviewer, reason, timestamp, candidate snapshot and product identity snapshot/hash. The detail page shows at most 25 recent events. A review is neither price approval nor proof of source rights, and it cannot publish.

Identical replays do not alter the original submitter or attestation, including legacy or CLI-created records; these must be investigated through a future controlled provenance workflow, not edited directly to bypass separation. The model's ordinary `save()`/`delete()` guard is **not** database immutability: bulk ORM operations and direct SQL can alter or delete history. The hash is a consistency fingerprint, not a signature or proof of untampered source provenance; the source URL is not part of the payload hash. PostgreSQL row locks protect rows actually locked, but product matching cannot prevent concurrent insertions or edits from creating ambiguity. A synthetic concurrent test demonstrates that a duplicate inserted after the fresh locked query can commit before the preliminary acceptance: a successful review is not a uniqueness guarantee. Separate tests exercise concurrent reviewer version checks, existing-row lock contention and a catalog edit during staging; these limited interleavings do not prove general concurrency safety. The review service rejects booleans, invalid and out-of-range IDs; hidden review/product version IDs are bounded by the PostgreSQL bigint range. See [ADR 0022](ARCHITECTURE_DECISIONS/0022-price-review-concurrency.md). Do not rely on this local workflow for real data or release decisions; production needs a designed isolation/locking strategy, transaction and concurrency tests against its actual DB, durable audit protections and independent security review.

## Receipt row consistency inspection

Receipt detail links to a separate private inspection for that same product or price domain. An active staff user needs that domain's candidate-view permission; receipt IDs from another domain return 404. The web inspection is read-only and DEBUG-only; authorized local service calls are not gated by that middleware. It checks manifest structural totals first, then scans at most 50 rows and one lookahead per request in data-row ordinal order, displaying only ordinals and fixed consistency statuses. A filter applies only to the scanned batch: an empty filtered result can still have a next link. Ordinal input accepts 1–19 ASCII, Persian or Arabic-Indic digits with values from 0 to 5000; arbitrary positions can skip earlier rows. Older receipts without a manifest are not reconstructed, and a structurally inconsistent manifest stops the scan.

The row comparison checks the current candidate against retained row identifiers and payload fingerprints, including the existing domain-specific structured-field validation; the historical price match is not recalculated. Within each joined page/batch, repeated references reuse pure candidate integrity validation, but each row is compared separately; the cache does not persist across pages or requests. This does not reduce staging writes. See [ADR 0026](ARCHITECTURE_DECISIONS/0026-receipt-validation-reuse-and-product-review.md). “No inconsistency detected” is only a limited technical result, not proof of source rights, identity, file integrity or data correctness. The aggregate, joined rows and successive pages are separate reads, not a snapshot: concurrent changes can affect results even within one request. The row cap does not bound SQL filtering/aggregate work, bytes or runtime. No raw fields or hashes are shown by this page, but receipt IDs and statuses are still private metadata. Use synthetic data only. See [ADR 0025](ARCHITECTURE_DECISIONS/0025-manifest-consistency-inspection.md).

## Presentation projection writes

A presentation's `search_text` and `irc_normalized` are derived lookup projections, not identity or verification. A nonempty `ProductPresentation.save(update_fields=...)` locks the existing row inside a transaction on the routed write database, reads omitted identity fields under that lock, and writes updated projections with the requested fields. Competing partial model saves of the same row wait; a lock can persist until an outer transaction ends. This can add latency or fail on deadlocks, timeouts and serialization errors; there is no automatic retry. Empty update fields are a no-op. Deprecated Django 5.2 positional save arguments are handled but callers should use keywords. Full saves still use the instance's values and can overwrite newer changes if the instance is stale.

Partial-save validation uses a prospective row assembled from the locked stored values and the explicitly written instance values, not stale omitted instance values. Existing invalid stored fields can therefore reject an unrelated partial update; explicitly correcting them can succeed. Signals still receive the original instance, whose omitted fields may remain stale. Normalization can expand an IRC past the 80-character projection column even when the input itself fits: full and partial model saves reject that with a validation error on `irc_normalized`, not truncation. Direct and bulk writes bypass this behavior. This does not validate other write paths or establish source correctness; see [ADR 0107](ARCHITECTURE_DECISIONS/0107-partial-presentation-validation.md).

Bulk ORM writes, direct SQL and historical migration models bypass the model override; they can still leave stale projections, as can existing records. No automatic backfill or repair is performed; a separate explicit one-row synthetic-only local repair exists. The bounded catalog-quality scan can flag some inconsistencies but does not prove complete coverage, identity or correctness. The row lock does not prevent new matching rows and does not fix the price-review concurrent duplicate limitation. See [ADR 0023](ARCHITECTURE_DECISIONS/0023-presentation-partial-save-projections.md).

## Synthetic projection repair (local CLI only)

For an isolated synthetic development database, `repair_catalog_projection` previews one internal presentation ID at a time. It is unavailable when `DEBUG` is false and has no web endpoint. It reports `consistent`, `unsafe`, or `needs_repair` and the affected projection names; only the last includes a short-lived token. The preview prints no product/source fields and makes no writes. For example, with a synthetic ID and after reviewing the preview:

```sh
DAROOBANK_DEBUG=1 .venv/bin/python manage.py repair_catalog_projection --id 1
# After reviewing the preview, provide its exact token via a protected non-terminal stream.
DAROOBANK_DEBUG=1 .venv/bin/python manage.py repair_catalog_projection --id 1 --commit --confirm-synthetic --token-stdin < /path/to/protected-synthetic-token-file
```

`--token-stdin` accepts a bounded single line from a non-terminal stream; it rejects multiple lines, terminals, oversized data and simultaneous `--token`. Provide a token only after the preview is reviewed and the required commit/attestation flags are present. This avoids placing the token in the repair command's argument list, but the preview output, source file, pipeline, OS-level access and logs still need protection; an open pipe can also block waiting for input. The legacy `--token` option remains supported but exposes its value in process arguments and potentially shell history. Never use real data or credentials in this synthetic tool.

Commit rechecks the signature, ten-minute expiry, database configuration and full observed row/expected projections while holding a row lock. A changed or deleted row, invalid token or unsafe source identity fails without a repair; preview again rather than guessing. The attestation is not proof that the data are synthetic. Only differing derived `search_text`/`irc_normalized` fields are changed, using a deliberate ORM update without model save signals. This can affect public search and price matching even though no publication flag changes. There is no automatic batch, repair audit, authorization or rollback log; backup and independently review any database before any administrative operation. Shell history, process listings and logs may expose IDs and tokens. The signature is not encryption or an authorization mechanism. Selected database write conflicts roll back and produce a generic error; the tool does not retry, and failures at a surrounding transaction's eventual commit are outside this boundary. `DEBUG` is a development gate, not a security boundary, and must never be enabled against real data for this tool. See [ADR 0024](ARCHITECTURE_DECISIONS/0024-synthetic-projection-repair.md) and [ADR 0063](ARCHITECTURE_DECISIONS/0063-projection-repair-conflict-boundary.md) for consistency checks, lock limits and remaining risks.

## Development-only PostgreSQL catalog inspection

The recorder primary-key index is also checked, but its rows are not verified; see [ADR 0089](ARCHITECTURE_DECISIONS/0089-postgresql-migration-recorder-columns.md) and [ADR 0092](ARCHITECTURE_DECISIONS/0092-postgresql-migration-recorder-primary-key.md). Selected auto fields require an owned sequence and identity-by-default or a canonical serial default referencing the sequence; equivalent noncanonical expressions can be flagged. Selected owned auto sequences also flag nonpositive increments, minimum below one or cycling, even if intentional. The current sequence value, function safety and insert success are not proven. See [ADR 0093](ARCHITECTURE_DECISIONS/0093-postgresql-auto-field-generation.md), [ADR 0094](ARCHITECTURE_DECISIONS/0094-postgresql-serial-default-clue.md) and [ADR 0103](ARCHITECTURE_DECISIONS/0103-postgresql-auto-sequence-sign-cycle.md). It flags nondefault null-distinctness, deferrable-only matches, nondefault operator-class flags and index-versus-column collation differences on selected simple unique keys, and counts unsupported model unique declarations as attention; a standalone immediate unique index may still match. See [ADR 0087](ARCHITECTURE_DECISIONS/0087-postgresql-unique-enforcement.md) and [ADR 0088](ARCHITECTURE_DECISIONS/0088-postgresql-unique-operator-collation.md). It does not compare all unique definitions, full column, constraint or index definitions to migrations, defaults, or column collation; see [ADR 0075](ARCHITECTURE_DECISIONS/0075-postgresql-column-clues.md), [ADR 0078](ARCHITECTURE_DECISIONS/0078-postgresql-column-type-clues.md), [ADR 0085](ARCHITECTURE_DECISIONS/0085-postgresql-unique-null-semantics.md) and [ADR 0086](ARCHITECTURE_DECISIONS/0086-unsupported-unique-declarations.md). It flags explicitly named model check constraints missing by table/name/type and exact deparsed `true`, `NULL::boolean` or `false` checks, but does not compare arbitrary expressions: same-named `CHECK (1 = 1)` or `CHECK (NOT true)` can pass. See [ADR 0104](ARCHITECTURE_DECISIONS/0104-postgresql-constant-check-clues.md) and [ADR 0105](ARCHITECTURE_DECISIONS/0105-postgresql-false-check-clues.md). It checks selected field-index coverage and named model index names, ordered key columns, sort directions, default null ordering, default operator-class flags, collation relative to the current column and absence of included columns, but not exact operator classes, column collation against model intent or plans; unsupported named indexes cause attention, and useful alternatives may be flagged. See [ADR 0081](ARCHITECTURE_DECISIONS/0081-postgresql-index-directions.md) through [ADR 0084](ARCHITECTURE_DECISIONS/0084-postgresql-index-collation-and-include.md). Database-generated field checks, FK match type, current transaction constraint mode, application data corruption, unscoped tables, partition children, privileges, backup quality and production readiness remain outside its scope; see [ADR 0080](ARCHITECTURE_DECISIONS/0080-postgresql-index-presence.md), [ADR 0072](ARCHITECTURE_DECISIONS/0072-postgresql-foreign-key-behavior.md), [ADR 0073](ARCHITECTURE_DECISIONS/0073-postgresql-unique-key-clues.md) and [ADR 0074](ARCHITECTURE_DECISIONS/0074-postgresql-check-constraint-names.md). A zero result is not a database health certificate. Use synthetic data only and restrict local access; DEBUG is not authorization. See [ADR 0070](ARCHITECTURE_DECISIONS/0070-postgresql-catalog-clues.md).

## PostgreSQL backup and isolated restore

PostgreSQL's `pg_dump` and `pg_restore` are external client utilities, not an application backup service. Use a client version at least as new as the server; access must be restricted and authorized. Dumps contain all user data, password hashes, sessions and other private information, are unencrypted by default and are not committed. Choose a trusted private location, encrypt and retain according to policy, and test restoration separately. A volume alone is not a backup. What this sequence does not prove is measured in [the backup and recovery plan](BACKUP_RECOVERY_PLAN.md) and [ADR 0232](ARCHITECTURE_DECISIONS/0232-backup-recovery-plan.md): the listing step discards the header in which an archive states when it was taken and from which database, `--no-owner --no-acl` restores 33 tables and no privileges, the archive holds every password hash and session row, and `manage.py check`, `migrate --check`, `inspect_postgresql_schema` and the drill's ORM verification all passed on an archive that was missing a fact written after it was taken. Restoring into a database that already exists is not described here at all.

For a **synthetic development** database, after exporting the PostgreSQL variables above and installing matching PostgreSQL client tools, set `SYNTHETIC_DUMP_FILE` to a new absolute file path in a trusted private directory. This example accepts only simple ASCII database names (letters, digits and underscores, at most 63 characters), not libpq connection strings or other valid PostgreSQL name forms. Run the **entire block together**, not individual lines. Each stage is conditional on the previous stage succeeding, including successful creation of the new target:

```sh
(
  set -C &&
  : "${SYNTHETIC_DUMP_FILE:?Set a new private archive path}" "${POSTGRES_DB:?Set the synthetic source database}" \
    "${POSTGRES_HOST:?Set the disposable PostgreSQL host}" "${POSTGRES_USER:?Set the PostgreSQL user}" &&
  export LC_ALL=C &&
  case "$SYNTHETIC_DUMP_FILE" in /*) : ;; *) printf '%s\n' 'An absolute archive path is required.' >&2; false ;; esac &&
  case "$POSTGRES_DB" in *[!A-Za-z0-9_]*) printf '%s\n' 'A simple synthetic database name is required.' >&2; false ;; *) : ;; esac &&
  [ "${#POSTGRES_DB}" -le 63 ] &&
  umask 077 &&
  export PGHOST="$POSTGRES_HOST" PGPORT="${POSTGRES_PORT:-5432}" PGUSER="$POSTGRES_USER" PGPASSWORD="${POSTGRES_PASSWORD:-}" &&
  pg_dump --no-password --format=custom --no-owner --no-acl --dbname="$POSTGRES_DB" > "$SYNTHETIC_DUMP_FILE" &&
  pg_restore --list --no-password -- "$SYNTHETIC_DUMP_FILE" > /dev/null &&
  createdb --no-password daroobank_restore_drill &&
  pg_restore --no-password --exit-on-error --single-transaction --no-owner --no-acl --dbname=daroobank_restore_drill -- "$SYNTHETIC_DUMP_FILE" &&
  POSTGRES_DB=daroobank_restore_drill .venv/bin/python manage.py migrate --check &&
  POSTGRES_DB=daroobank_restore_drill .venv/bin/python manage.py check
)
```

The example directory must already exist and be private. `set -C` requests shell noclobber; verify filesystem and shell behavior, and never use an untrusted directory. A failed dump can leave an incomplete file and a failed restore can leave the newly created database; inspect and clean up only after independently verifying their identity. If the target already exists, `createdb` fails and this block does not start restore. Do not run the commands separately or use the target concurrently. This is not atomic backup publication or a general safeguard against misconfigured hosts or inherited libpq settings; absolute paths can still contain symlinks. See [ADR 0091](ARCHITECTURE_DECISIONS/0091-synthetic-backup-guide-fail-stop.md) and [ADR 0102](ARCHITECTURE_DECISIONS/0102-synthetic-backup-argument-guards.md). PostgreSQL/OS environment variables can be visible to privileged local processes; use an appropriate secret manager or restricted `.pgpass` for production. Set `PGSSLMODE` and certificate variables as required. `createdb` needs privileges and must target an isolated test server; remove drill databases only under an explicit local retention policy. `pg_restore --list` checks the archive structure, not the restored data; check expected records, relationships and application behavior on the isolated copy. Database-only dumps do not include roles, external assets or all cluster configuration. `migrate --check` only checks pending migrations. Restore commands never target the active database. No automatic encryption, off-host retention, cadence or monitoring is provided; see [ADR 0007](ARCHITECTURE_DECISIONS/0007-backup-policy.md).

## Concurrent PostgreSQL CSV staging

Committed product and price CSV stages take a transaction-level PostgreSQL advisory lock keyed by the staging domain and **exact validated source URL**. This also applies to the direct import services and CLI commit paths; preview never acquires the lock. The lock is held until the outermost transaction commits or rolls back, including any receipt and manifest writes. Same-domain, same-URL stages wait rather than interleave their overlapping unique-key inserts in opposite order. File row order and manifest ordinals remain unchanged; replay still creates a separate web receipt while preserving the first candidate recorder.

This protocol coordinates only participating current-version writers. Older workers, direct SQL and bulk writes bypass it; different URL spellings do not share a key. Different domains and URLs normally do not wait on each other, though hash collisions can serialize unrelated stages. Waiting can be prolonged by an outer transaction or slow code; there is no application-level timeout, fairness or automatic retry. A configured PostgreSQL lock timeout can cause an error and transaction rollback. Do not call another staging operation or external service from row callbacks; taking several source locks in inconsistent orders can deadlock. Deploy the same protocol across writers. This is not a network authorization, matching lock, audit or exactly-once guarantee. See [ADR 0010](ARCHITECTURE_DECISIONS/0010-staging-concurrency.md).

Account and receipt reads are separate, and showing a current name is not verification of historical identity, authority, source rights or the receipt itself. The candidate's related-receipt clues and the manifest inspection do not check receipt-actor existence, and inspection also does not check candidate-stager existence. Existing domain permissions still apply. Synthetic data only; see [ADR 0035](ARCHITECTURE_DECISIONS/0035-missing-receipt-actors.md).

### Identity package reviews with missing accounts

Package history resolves the reviewers of up to 25 visible reviews in one separate query, and the correction page resolves its latest reviewer. Missing reviewers keep their rows and latest version but details are hidden; a missing account alone does not prevent later review or correction. The account lookup is not a snapshot or verification of past identity, authorization or qualifications. Graph and revision-link structural checks do not assess current creator-account presence; selected graph writers now check it separately as described in ADR 0037. Do not treat hash or graph consistency as authenticity, source rights or clinical approval. Use synthetic data only; see [ADR 0036](ARCHITECTURE_DECISIONS/0036-identity-reviewer-lookup.md).

### Identity graph creator presence in writes

Dependent identity creation, package review and component/package correction check that creators in the selected current graph exist after structural validation. They reject a missing account without writing. A graph has at most eight distinct creator IDs; each check uses a single bulk account query, while nested correction/creation may check more than once. Existing inactive accounts still count, users are not locked, and graphs may be read at different moments. Displays, structural classifiers and lineage do not check creator existence; earlier correction ancestors and link actors are not checked. This is not proof of identity, authorization, source rights or clinical accuracy. Use synthetic data only; see [ADR 0037](ARCHITECTURE_DECISIONS/0037-identity-graph-creator-presence.md).

### Identity package immediate product lock

Package review and package correction lock the selected package, then re-read and lock its immediate product before reconstructing and validating the graph. A missing product conflicts. Locks persist until the outer transaction completes and may add wait time or deadlocks; there is no automatic retry. ADRs 0039 and 0040 subsequently add formulation and bounded existing component/ingredient row locks; account checks have no exclusive user locks, and new or later changes can still stale the graph. Only selected PostgreSQL schedules were tested; this is not a graph-wide snapshot, provenance, source authorization or production guarantee. Direct non-string review decisions now conflict; malformed HTTP forms return 400. Synthetic data only; see [ADR 0038](ARCHITECTURE_DECISIONS/0038-identity-package-product-lock.md).

### Identity package formulation lock

Package review and correction lock the package, product and then re-read/lock the product's formulation before building the graph; missing formulations conflict. Locks last until the outer transaction ends. ADR 0040 subsequently adds bounded existing component/ingredient row locks and extends selected other writers. Missing-row predicates and exclusive user locks remain outside this check; new and later changes may stale the graph. Lock waits/deadlocks and timeout failures remain possible without automatic retries. Selected tests cannot establish full isolation or authenticity. Synthetic data only; see [ADR 0039](ARCHITECTURE_DECISIONS/0039-identity-package-formulation-lock.md).

### Identity graph component and ingredient locks

Package review/correction, dependent product/package creation and formulation/product correction lock existing components (at most five valid rows, plus one sentinel) and their ingredients in ascending primary-key order after applicable parent locks, then reconstruct the graph. Missing/inconsistent rows conflict; nested operations may repeat checks. Locks last until the outer transaction ends, can cause waiting or deadlocks, and have no retry. They are not predicate locks: a tested deferred concurrent insert committed after review and made its saved graph stale. Same-transaction bypasses and later changes remain possible. Current account existence is separate, not proof of identity or authority. Only synthetic data; see [ADR 0040](ARCHITECTURE_DECISIONS/0040-identity-components-and-ingredients-locks.md).

### Latest identity package review lock

Package review and correction also lock the latest existing review after the graph row locks, through the outer transaction. Correction validates it; new review creation checks its ID only. No older or absent review row is locked, and display reads are unchanged. Deferred concurrent inserts, later writes and same-transaction bypasses can change history; waiting and deadlocks remain possible without retry. See [ADR 0041](ARCHITECTURE_DECISIONS/0041-identity-latest-review-lock.md).

### Selected identity concurrency errors

The selected identity graph writer atomic boundary converts PostgreSQL SQLSTATE 55P03, 40P01 and 40001 to `IdentityConflict` only after rollback of that boundary; existing private HTTP flows return 409. Unrelated errors are re-raised. This sets no timeout and does not retry. A failure at a later outer commit is outside the boundary; after deadlock or serialization failure abandon/retry the entire enclosing transaction as appropriate, not just the inner operation. See [ADR 0042](ARCHITECTURE_DECISIONS/0042-identity-write-concurrency-errors.md).
