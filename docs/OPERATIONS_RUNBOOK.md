# Operations runbook

This is mostly a prospective checklist; a local development web process and PostgreSQL-native backup guidance exist. No production services, dashboards, alerts or on-call rotation currently exist. Create concrete commands, owners and escalation contacts before production.

## Source or worker incident

1. Confirm source health and rights/expiry, inspect run status, counts, pagination coverage, checkpoints and sanitized errors. Distinguish partial, failed and complete runs.
2. Pause the affected source and disable automated publication on schema drift, unexpected empty data, price/currency anomalies or permission uncertainty. Do not delete products or change approved prices due to absent records. Keep last verified data with freshness warning.
3. Escalate to data steward/source owner. Fix adapter against authorized fixtures, rerun in staging, then explicitly resume from a safe checkpoint. Verify idempotency, complete coverage and candidate review. Record incident, remediation and approvals.

## Bad price or clinical claim

Withdraw or supersede the publication through an authorized auditable decision; preserve original evidence and history. Invalidate caches, record affected scope and time, notify clinical lead and affected users where legally appropriate, investigate root cause and correct only with evidence. Never silently rewrite history. For serious harm risk escalate through the clinical incident protocol.

## Restore and recovery

Before deployment, define ownership, encrypted backup cadence, off-host retention, RPO/RTO and recovery environment according to business and legal requirements; no values have been approved. Test restoring database and authorized objects together, permissions, audit integrity, point-in-time consistency and application compatibility. Record actual restore duration and recovery point; conduct periodic drills. The only restore durations this repository has are measured in [the backup and recovery plan](BACKUP_RECOVERY_PLAN.md) and [ADR 0232](ARCHITECTURE_DECISIONS/0232-backup-recovery-plan.md): 0.071 s to dump and 0.163 s to restore a 33-table, two-account synthetic fixture, plus 1.673 s of verification, and no cadence, custodian, owner or objective has been approved. If queue state is lost, use DB checkpoints and idempotent replay rather than treating broker as audit source.

## Security/privacy incident

Contain, preserve evidence, restrict access/rotate exposed credentials and engage security, legal and clinical owners. Assess PHI exposure and regulatory notification duties with qualified counsel; keep sensitive data out of incident tickets. Verify recovery after restoration. There are no application access or audit logs to review ([ADR 0221](ARCHITECTURE_DECISIONS/0221-no-read-audit.md)): whatever request history exists has to come from the proxy, the database or the host, and has to be arranged and retained before deployment. Define the on-call chain before enabling patient accounts.

When the account behind a staff session is the problem, the session has to end and not come back. Every staff session is bound at login to a digest of the account state it was created against, and a middleware ends a session whose account differs from it, so deactivating an account, removing `is_staff`, changing a permission or a group, deleting the account or changing its password ends the session on its next request ([ADR 0213](ARCHITECTURE_DECISIONS/0213-durable-session-invalidation.md)). That leaves one gap: a transition nobody observed leaves a dormant session in the store. `manage.py list_staff_sessions` reports, per account, which sessions exist, which are unbound and which the guard would end — listing aliases rather than session keys, so the output is not a credential dump ([ADR 0214](ARCHITECTURE_DECISIONS/0214-session-inventory.md)) — and `manage.py revoke_staff_sessions --username <name> --apply` deletes that account's sessions without waiting for a request, while `--all --apply` clears every authenticated session at once. It cannot clear the sessions a secret rotation invalidated: a rotated key leaves those rows undecodable, so `--all --apply` reports `matched: 0, revoked: 0` and leaves them in place, and `manage.py list_staff_sessions` reports `sessions_matched: 0` for the same reason ([the secret-rotation plan](SECRET_ROTATION_PLAN.md), [ADR 0231](ARCHITECTURE_DECISIONS/0231-secret-rotation-plan.md)). Both are read-only without `--apply`, delete at most one bounded batch and print one JSON object. Both commands are read-only or bounded, refuse to run outside a synthetic development environment, and are **not** a production procedure: who may run them, what is audited and what is retained is an open gate. Restoring the account state afterwards does not revive an ended session.


## Deployment readiness check

`python manage.py check_deployment_readiness` reads this process's settings and its migration table, writes nothing and prints one JSON report: ten required checks decide `ready` and the exit status (0 ready, 1 not), and a separate `review` list carries conditions that need a decision rather than a fix — HSTS off, HTTPS redirection with no trusted proxy header, development hostnames in `ALLOWED_HOSTS`, health probes answering, the synthetic login limiter, `XFrameOptionsMiddleware` absent. `--strict` also fails while any review item is present. Run it once per process, before and after a deploy, and keep the output with the release record so two releases can be compared. Its two migration checks read the migration table only, so a database that a cancelled rollback left half undone reports the same `1 migrations are not applied` as one that has not been upgraded yet, while `check`, `makemigrations --check --dry-run` and `showmigrations` exit 0 on it and repairing forward returns an identical schema without returning a row; what every command in this tree says about that state is measured in [the database migration plan](DATABASE_MIGRATION_PLAN.md) ([ADR 0233](ARCHITECTURE_DECISIONS/0233-database-migration-plan.md)).

It is not monitoring and not an authorization: it serves no request, checks nothing about collected static files, logging, clocks, connection pooling, replicas or external dependencies, and a zero exit status does not mean this process may be deployed ([ADR 0217](ARCHITECTURE_DECISIONS/0217-deployment-readiness-report.md)). In a development environment it is expected to report not ready and to say why.

The edge conditions in that review list are now measured rather than assumed: both header profiles over the public and staff routes, the HSTS and forwarded-scheme matrices, the absence of any `Access-Control` header, the 7-of-12 referrer split and the opt-in limiter's 429 refusal are recorded in [the network and TLS plan](NETWORK_TLS_PLAN.md) ([ADR 0234](ARCHITECTURE_DECISIONS/0234-network-tls-plan.md)); the plan is a proposal with no owner and implements nothing.

The connection and capacity conditions in that same review list are measured too, on a synthetic server and throwaway databases: a request at the default lifetime opens one connection and pays about 2 ms for it against about 0.1 ms for the query it runs, the cluster refuses a 98th non-superuser connection with *"remaining connection slots are reserved for roles with the SUPERUSER attribute"* and a 101st with *"sorry, too many clients already"*, an idle backend holds about 1,104 kB of proportional set rather than the 10,347 kB of resident set it reports, no statement, lock wait or idle transaction is bounded by the server, a least-privilege role's `VACUUM` exits 0 while `vacuum_count` stays 0, and a base backup of the whole cluster took 1,214 ms and 8,058,024 bytes with `archive_mode` off, so it recovers to the instant it was taken and to no point after it ([the database connection plan](DATABASE_CONNECTION_PLAN.md), [ADR 0235](ARCHITECTURE_DECISIONS/0235-database-connection-plan.md)).

## Local synthetic restore drill

Use the [PostgreSQL backup and isolated restore procedure](DEVELOPMENT_GUIDE.md#postgresql-backup-and-isolated-restore) only with synthetic data and a newly created isolated database. Verify migrations, records and application behavior; never restore into the running database. Record the outcome without sensitive details, then dispose of copies under the local policy. These steps are not a production restore exercise; no cadence, encryption, off-host retention, recovery objectives, alerting, external asset recovery or production access controls are implemented. The drill restores into a database it just created and verifies a fixture the same process wrote, which is why an archive missing a fact written after the dump passed every check it runs; see [the backup and recovery plan](BACKUP_RECOVERY_PLAN.md).
