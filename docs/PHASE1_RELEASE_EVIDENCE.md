# Phase 1 foundation: evidence and outstanding decisions

This is a working checklist, **not** an approval, a percentage complete, a production runbook, or evidence that patient data may be used. The local application and every test dataset must remain synthetic. The Phase 1 scope and broader dependencies are in [the roadmap](ROADMAP.md); security and operational controls are described in [Security](SECURITY.md) and [Deployment](DEPLOYMENT.md).

**Status key:** `development evidence` means a limited local implementation or exercise exists, not that an operational gate has passed. `open` means a decision or implementation remains. Items can have both statuses. Owners and dates are intentionally not invented: the project must assign them.

| Area | Development evidence | Outstanding gate / evidence to collect before any production authorization |
|---|---|---|
| Architecture and hosting | ADRs and a modular Django/PostgreSQL skeleton exist. | **Open:** owners approve architecture, data classification, provider/region, legal and operational responsibilities; assess connectivity, vendor and data-residency constraints. Document decisions and exceptions. |
| Data model and migrations | Migrations and PostgreSQL-backed synthetic tests exist, and the rollback direction is now measured: on throwaway PostgreSQL databases the suite migrates, rolls back and reapplies 17 migrations across six apps, requires each app to be one linear chain, requires every data operation to declare an explicit reverse and names the two whose reverse is a no-op, derives the cascade of a single-app rollback from the migration graph (rolling catalog back unapplies exactly 11 migrations, its own eight plus pricing's two and ingestion's one, and leaves no foreign key without its target), and requires the column, index and constraint inventory after a full rollback and reapply to be identical to the first migration — 33 tables, 279 columns, 111 indexes, 138 constraints, 50 foreign keys and 32 applied rows on a freshly migrated database, checked against the same model-derived expectations CI applies to the development database. `makemigrations --check --dry-run` also runs inside the suite, mirroring the CI step (ADR 0216). The same drill now runs on a **populated** throwaway database — 31 synthetic rows across all 24 project tables plus one staff account that wrote them — and measures what a rollback costs: rolling catalog back destroys 23 of those 31 rows and orphans an import receipt whose item table is gone, rolling all six apps back destroys every project row while `auth_user` keeps the account that wrote them, reapplying returns an identical inventory and zero rows, a copy taken beforehand restores rows only in foreign-key order and only after `setval` advances the identity sequences the copy reused, and a rollback attempted while a second session holds one product row `FOR UPDATE` fails on `lock_timeout` after its first migration already committed — leaving 31 of 32 migrations applied, 29 of 31 rows and a half-undone schema that migrating forward repairs without restoring a row (ADR 0225). Both directions now carry a clock and a WAL counter, at three volumes and under a write load, on throwaway databases: `migrate` applies 32 migrations in 0.927 s and 1,172,320 bytes, `migrate catalog zero` unapplies its 11-migration cascade in 0.711 s, all six apps leave nine tables in 0.378 s, reapplying returns an identical 279-column inventory in 0.724 s with zero rows, and a rollback of 50,000 rows costs 0.096 s and 6,680 bytes against the 29,621,944 bytes inserting them cost — so a duration cannot gate a rollback. A rewriting `ALTER TABLE` over 500,000 rows takes 3.631 s and 178,759,168 bytes and, under a writer committing about 175 times a second, waits 2.726 s and stalls exactly one insert for 2.703 s, while a metadata-only `ADD COLUMN` takes 0.001 s and blocks nobody; one session that is only reading cancels either at a 2 s `lock_timeout` after 2.001 s and cancels `migrate catalog zero` after 2.551 s into the same half-undone state, which `check`, `makemigrations --check --dry-run` and `showmigrations` report as clean while `migrate --check` exits 1 and readiness names one unapplied migration — the signal an unmigrated database gives. `migrate contenttypes zero` is the widest command in the tree, a cascade of 26 migrations of which 24 are project migrations leaving five tables and six rows; `migrate sessions zero` is one migration and costs `django_session`; the validated `catalog 0008` constraint scans 200,000 rows in 0.100 s and 2,464 bytes and refuses one violating row after 0.052 s without being recorded; no migration connection carries a timeout (`db_options` is `{'connect_timeout': 5}`) and no migration module is non-atomic, so none can build an index concurrently; and a copy at that volume is 1,186,535 bytes in 0.154 s and restores in 0.327 s with its sequences intact, needing no `setval` ([the database migration plan](DATABASE_MIGRATION_PLAN.md), [ADR 0233](ARCHITECTURE_DECISIONS/0233-database-migration-plan.md)). | **Open:** the gate this row carried — *"a staging upgrade and rollback **plan** — environment, order, backup and restore step, owner and authorization for a destructive operation"*, whose own list of gaps was *"it measured no duration, no WAL volume and no long-running `ALTER TABLE` under load"*, *"No backup, restore tool, recovery objective or copy of the tables a cascade will drop exists; a failed rollback has to be repaired by hand"* and *"Rollback of Django's own apps, other shapes of concurrency (an open writing transaction, `CREATE INDEX CONCURRENTLY`, a running command, a standby) and tested recovery from a real staging schema are unmeasured"* — is now measured and priced, and stays open. [DATABASE_MIGRATION_PLAN.md](DATABASE_MIGRATION_PLAN.md) carries eight numbered decisions and seven priced options ([ADR 0233](ARCHITECTURE_DECISIONS/0233-database-migration-plan.md)) and names no owner, no environment, no order and no authorization, because a proposal is not a staging environment and nothing is implemented: this tree defines no staging environment, no migration connection carries a `lock_timeout`, no copy is taken before a destructive migration, no command distinguishes a half-undone schema from an unmigrated one, and a failed rollback still has to be repaired by hand. Every duration, WAL volume, lock mode and concurrency shape the gate listed as unmeasured is measured once, on synthetic throwaway databases at 31, 50,031 and 500,000 rows, and one run on one machine is not a budget: no representative volume, connection pool, vacuum or checkpoint pressure and no real workload was measured. Two of the named shapes stay unmeasured — a running management command was not held open against a migration, and a standby cannot be measured here because this environment has no replica (`pg_is_in_recovery()` is false and both replication views are empty) — and tested recovery from a real staging schema is impossible in a tree that has no staging schema. |
| API and permissions | Versioned OpenAPI and selected server-side authorization tests exist, plus a route-by-route staff authorization matrix over 41 `staff_*` routes and six synthetic account shapes, repeated against real rows for the 23 object routes so a denial cannot become an existence oracle, with a coverage assertion tied to the live URL resolver (ADR 0200–0201). Every non-staff route is likewise inventoried from the resolver and probed for private-data leakage with two positive controls (ADR 0202), and the same staff matrix is repeated for group grants, an active superuser, a superuser without `is_staff`, a deactivated account and an alternate authentication backend (ADR 0203). Denials for existing and missing rows are also compared byte-for-byte in status, body and headers, so a route cannot leak existence through content (ADR 0204), and the same routes are probed with thirteen identifier shapes and both method directions so a malformed identifier or a wrong method cannot be distinguished per account (ADR 0205), and nine caller-controlled query shapes across all 41 staff routes cannot change a denial, cause a server error or widen a kind filter (ADR 0206). The CSRF gate is measured across all 43 staff routes: a token-less post yields one canonical 403 for five account shapes, five token failure modes are indistinguishable, and with a valid token each route answers exactly as its view decorators declare (ADR 0207). Logout, cookie replay, a password change and forced session expiry are each walked across all 41 routes behind a positive control (ADR 0208); the open blocker in ADR 0191 is unchanged by this. Six HTTP methods are swept across all 43 staff routes, pinning that no destructive method is accepted, that `Allow` advertises only declared methods, and that a method rejection is identical for every account shape (ADR 0209). The whole header surface of those routes is then pinned: across 1 204 responses (43 routes × 7 methods × 4 accounts) seven privacy headers must appear with exact values, `Allow` only where a method was refused, `text/csv` and `Content-Disposition` only on the two sample downloads, and no header at all outside a closed inventory (ADR 0210). Redirect targets are probed with 21 caller-supplied `next` values across both authentication endpoints and all 41 routes: a hostile value never becomes a target, an anonymous redirect always lands on the login page with the requested staff URL as its return target, and the login form echoes only the validated value (ADR 0211). The whole inventory is collected in [the authorization review](AUTHORIZATION_REVIEW.md), where both tables are generated from the live resolver and the pinned suites rather than typed, a drift test re-renders them, and every cited ADR is checked to exist (ADR 0215). `django.contrib.admin` is deliberately not installed — the roadmap's "auth/admin baseline" is the hand-built portal — and seven tests pin that absence: the installed-app list, seven admin paths that do not resolve, a byte-identical 179-byte 404 for an anonymous caller and a superuser, no `django_admin_log` table, no project import of the admin, no third surface in the resolver, and the five operational commands that replace admin screens (ADR 0218). | **Open:** the review's *judgement* — approve each route's requirement, approve exposure and permissions for the intended deployment, and add threat modeling and an independent security assessment. The review document lists these as unanswered questions with blank owner and date columns; nothing in it is a sign-off. |
| Staff authentication | Debug-only staff portal and opt-in synthetic IP-window limiter exist; duplicate login fields are rejected. Sixteen guarded write services across fourteen staff routes (source-claim creation and review, price review, clinical review, product review, product and price staging, clinical draft create/revise and reference create, and the seven identity workspace writes) recheck account flags, permissions and the session password hash inside their transactions through one shared helper, and all fourteen staff write routes have synchronized in-flight tests plus a route inventory drift guard (ADR 0192–0199). Sessions are now bound at login to a digest of the account state and a middleware ends a session whose account differs from it, read from the account the session names rather than from `request.user`, so deactivation, staff-flag removal, permission and group changes, account deletion and password changes delete the session row and restoring the state does not revive it; a bounded development-only command revokes the sessions of one account or all of them for the transition no request observes, and a read-only inventory reports, per account, which sessions exist, which are unbound and which the guard would end — listing aliases rather than session keys (ADR 0213–0214). | **Open:** MFA enrollment and recovery, replay protection for a stolen cookie whose account state never changes, an approved production revocation and inventory procedure with access control, audit and an owner, production-grade account and network abuse controls, proxy identity, alerting and independently reviewed policy. The current limiter is not a production control, and the guarded-write rechecks cover sixteen services and selected orderings, not other writes, permission races, the unlocked rechecks, preview or actor-less staging. The session guard fires only when a request arrives, so an off/on transition that no request observes leaves a dormant session usable until it is revoked explicitly, and removing an authentication backend from settings is not observable at request time. See the unapproved [MFA implementation plan](MFA_IMPLEMENTATION_PLAN.md), which now measures this tree and prices six options for a second factor, [ADR 0230](ARCHITECTURE_DECISIONS/0230-mfa-implementation-plan.md), which records that measurement and implements nothing, the [session revocation record](ARCHITECTURE_DECISIONS/0191-staff-session-revocation-gap.md) and [ADR 0213](ARCHITECTURE_DECISIONS/0213-durable-session-invalidation.md). |

| Backups and recovery | Synthetic PostgreSQL dump/restore and encrypted-envelope negative controls exercise a limited local scenario. | **Open:** encrypted off-site backups, independent key custody, access control, retention, integrity and anti-replay/freshness policy, recovery objectives, scheduled isolated restore drills and documented owner. | Monitoring and response | Minimal opt-in process and PostgreSQL probes exist, and `manage.py check_deployment_readiness` now collects the wider shape into one read-only JSON report: ten required checks (debug off, staff portal off, secret and host shape, secure session and CSRF cookies, the session flags ADR 0208 pins, HTTPS redirection, no pending migrations, no applied migration without a file in this release, and a reachable database) plus a separate list of conditions that need a decision rather than a fix, with `--strict` failing on those too. Every required check is measured to be able to fail on its own, the report never contains the secret value, two runs of one configuration are byte-identical, and the command writes nothing (ADR 0217). All sixteen environment variables the application reads are now inventoried from the code and documented per audience, including a deployment configuration reference that states the production expectation for each (ADR 0222). What the application does not protect against is measured too: no rate limit is on by default on any public route, no request-size ceiling is configured and nothing answers 413, so rate and size limits are external work assigned in the deployment guide (ADR 0223), and the two limiters that do exist are both opt-in — the debug-only login window, and a public read limiter that counts 120 reads per keyed client in a rolling minute, refuses an over-limit read with 429 and a `Retry-After`, stores only a keyed digest, a window start and a count, fails open when the counter is unreachable, and has no command to prune its rows (ADR 0228). What is not monitored is measured too: the application records no read at all — `LOGGING` is empty, no module imports `logging`, no middleware records a request, no table can hold an access record, and sweeping all 55 routes creates no row (ADR 0221) — so any request history has to come from the proxy, the database or the host. What adding one would cost is measured rather than estimated: `docs/READ_AUDIT_PLAN.md` records the six decisions that block it and a reverted prototype of the in-application option — one append-only table, its migration and a row-per-GET middleware behind a new setting — which failed 20 pins across 7 of the 9 sampled suites and measured 33 tables, 283 columns, 113 indexes, 139 constraints, 51 foreign keys and 32 applied migrations against the 32, 276, 108, 136, 50 and 31 of that day (ADR 0227). | **Open:** private access restrictions, network/request deadlines, monitoring, alert routing, on-call ownership and incident response. The readiness report describes one process's settings and one database connection in the environment that runs it: no request is served, no static-file, logging, clock, pooling, replica or external-dependency condition is checked, and it has never been run against a real deployment, so "production-specific" readiness is still unproven. Probe success proves neither migrations nor recovery, and a zero exit status is not a deployment authorization. No component records that a read happened, and the read-audit decision — scope, reader identity, retention, tamper-resistance, placement and enablement — is written as a proposal with no owner, so the runbook's instruction to review access and audit logs after a restore still cannot be followed inside this application. |
| CI and supply chain | GitHub Actions runs development tests and selected dependency scans, and the workflow's shape is now pinned: one workflow of two jobs and 22 steps triggers only on push and pull request, holds exactly `contents: read`, pins all five action references to 40-character commit SHAs with their versions commented, disables checkout credential persistence, installs both hash-pinned lock files with `--require-hashes` behind a negative control that requires pip to reject a zeroed hash, verifies the runtime lock first and audits the resolved dependencies and the built image with `pip-audit --strict` (ADR 0226). | **Open:** independent review, immutable production artifacts and image digests, OS/transitive dependency review, staging/release gates and rollback. CI produces no artifact at all: nothing is uploaded, tagged, pushed, described by an SBOM or signed, no step exports a value a later gate could read, no job waits on another or runs in a protected environment, and all four base-image references (`postgres:16` three times, `python:3.11-slim` once) are mutable tags rather than digests, so the same commit can build a different image. The only image the repository can build is a development image — untagged, root-owned, serving through `runserver`, destroyed inside the run. CI success is not a security certification. |

## How to close a gate

1. Assign an accountable owner, scope, decision deadline and applicable environment; link an approved policy or decision record.
2. Capture dated, reproducible evidence and exceptions without placing secrets, patient data or sensitive infrastructure details in this repository.
3. Have the relevant independent security, operations, legal or clinical reviewer approve the evidence where applicable. A successful local test is supporting evidence only.
4. Obtain explicit authorization before provisioning or deploying production infrastructure, importing real data, or publishing clinical/price claims. Record rollback and incident ownership separately.

A working development control must not be promoted to a passed operational gate merely because it appears in this checklist. See [Testing strategy](TESTING_STRATEGY.md) for exact test scope and known gaps.
