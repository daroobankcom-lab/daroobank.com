# Security and privacy strategy

Django escaping, HTTPS source validation, bounded queries and basic security headers are implemented and tested in the development slice. A limited same-origin content-security policy is enforced on Django responses, with explicit exceptions and important deployment limitations described in [ADR 0121](ARCHITECTURE_DECISIONS/0121-development-content-security-policy.md). Most controls below remain proposed; these are not proof of compliance or production readiness. Iranian legal, professional, data residency and telehealth obligations require advice from qualified local counsel and review by clinical governance before handling patient data or launching consultations.

## Threats and access

Protect against unauthorized price/content changes, account takeover, source poisoning, malicious uploads, PHI leakage, API abuse, privilege escalation and supply-chain compromise. Default deny; server-side object-level authorization and separation of author/reviewer. Users may hold multiple roles; implement auditable permission grants, revocation and periodic review.

| Role | Proposed scope; not automatically granted |
|---|---|
| Super administrator | Manage roles/security configuration; no automatic clinical approval bypass. |
| Database administrator | Operate backups and database, not editorial publication by default. Measured today: no custodian, cadence, off-host copy or owner exists, and what a local drill proves is measured in [the backup and recovery plan](BACKUP_RECOVERY_PLAN.md) ([ADR 0232](ARCHITECTURE_DECISIONS/0232-backup-recovery-plan.md)). |
| Content editor | Draft/submit clinical content, not approve own work. |
| Pharmacist/medical reviewer | Review/approve clinical content within qualification, not own drafts. |
| Pricing administrator / verifier | Review prices, source evidence and corrections within assigned scope. |
| Crawler operator | Run/pause/retry jobs and configure schedules, no clinical approval. |
| Consultation professional | Access only assigned, consented consultations after verified licensure; disabled initially. |
| Registered user | Own profile and future consented records only; no admin data. |

## Controls

MFA for administrators, secure sessions, CSRF, Argon2-compatible password hashing, rate limits, lockout/recovery controls and scoped expiring API credentials. TLS in transit; encryption at rest where appropriate with isolated managed keys and rotation; least-privilege DB/worker credentials. Validate inputs and sanitize display; CSP, security headers, safe dependencies, restricted egress and bounded uploads with malware scanning and private storage. Keep secrets in a secrets manager/environment, never in Git; the existing `.env.example` contains placeholders only. Measured today: there is one secret, `DAROOBANK_SECRET_KEY`, and every keyed digest in the project inherits it — 9 `salted_hmac` sites in 9 modules, none passing its own `secret=`, 6 modules signing through `django.core.signing`, and a session store that signs its own rows. No rotation procedure, fallback configuration or rotation record exists; rotating the key ends every staff session at its next request, empties the rows it invalidates, hides them from both session commands, restarts both address-keyed limiters, denies guarded writes rechecked with the old hash and leaves one unhandled `Session data corrupted` warning behind ([the secret-rotation plan](SECRET_ROTATION_PLAN.md), [ADR 0231](ARCHITECTURE_DECISIONS/0231-secret-rotation-plan.md)). How much key there is, and where its value can be read, is measured separately in [the secrets and access plan](SECRETS_ACCESS_PLAN.md) ([ADR 0238](ARCHITECTURE_DECISIONS/0238-secrets-access-plan.md)): the shape guard accepts a 50-character key carrying 28.1 bits and rejects ones carrying 96.1 and 156.1 bits, so it is not monotonic in entropy, while an entropy floor of 100, 150 or 200 bits would change the verdict of 0 of the nine key literals in the tree and the one literal the guard accepts is a 249.3-bit test fixture; the value leaves a running process in exactly one measured channel, `/proc/<pid>/environ`, readable by the uid the server runs as, and appears in 0 of 29 routes, 0 log bytes and 0 tracked files; a debug error page masks by name, printing 10 of 154 settings as stars while a setting named `PEPPER`, every POST field and every frame local would print in clear, and 0 tracked files use the two decorators that would mask them; the debug fallback is committed, so a search cursor minted offline under it verifies and a login-throttle key is computable without the server; nothing in the tree can produce a key, 0 of the 12 commands can say who holds one, and 6 document lines ask for an approved secret manager while 0 name a mechanism — an unowned proposal that implements nothing.

Audits record actor, role, target, before/after versions or hashes, decision, time and request correlation, without PHI in general logs. Protect audit from modification by application roles and monitor unauthorized access. Measured today: no component of this application records that a read happened — `LOGGING` is empty, no project module imports `logging`, no middleware records a request, and no table in the schema can hold an access record, while the four revision tables record writes and name their actor. A staff sweep of all 43 staff routes and an anonymous sweep of all 12 public routes create no row anywhere ([ADR 0221](ARCHITECTURE_DECISIONS/0221-no-read-audit.md)). [`READ_AUDIT_PLAN.md`](READ_AUDIT_PLAN.md) records the decisions that block adding one — scope, reader identity, retention, tamper-resistance, placement and enablement — with the measured price of the in-application option: a reverted prototype of one append-only table, its migration and a row-per-GET middleware failed 20 pins across 7 suites ([ADR 0227](ARCHITECTURE_DECISIONS/0227-read-audit-plan.md)). Separate production and non-production data; synthetic data only in tests. Backups encrypted, access controlled and regularly restore-tested.

TLS in transit is required by this strategy but not established by this repository: what the edge actually emits in both configurations — HSTS off at 0 of 3 features, no `Access-Control` header anywhere, `X-Forwarded-Proto` stripped without the reviewed opt-in, secure cookies only in non-debug — is measured in [the network and TLS plan](NETWORK_TLS_PLAN.md) ([ADR 0234](ARCHITECTURE_DECISIONS/0234-network-tls-plan.md)), an unowned proposal that implements nothing.

The database half of the least-privilege requirement above is measured rather than met: every connection this application makes uses the cluster's one non-system role, a superuser that owns all 33 tables, and from it a session read a stored `SCRAM-SHA-256` hash out of `pg_authid`, dropped and recreated a project table, created a database and installed an extension. A throwaway `LOGIN NOSUPERUSER` role holding `SELECT, INSERT, UPDATE, DELETE` read and wrote the same tables and was refused `pg_authid`, `CREATE TABLE`, `CREATE DATABASE`, `ALTER TABLE`, `CREATE INDEX`, `TRUNCATE`, `REINDEX`, `ALTER SYSTEM` and `SET ROLE`; it could not run migrations without `CREATE` on the schema, could not create the test database the runner needs, could not read another role's query text — which reads `<insufficient privilege>` where the superuser reads the statement — and its `VACUUM` and `GRANT` reported success with a warning while changing nothing ([the database connection plan](DATABASE_CONNECTION_PLAN.md), [ADR 0236](ARCHITECTURE_DECISIONS/0236-database-connection-plan.md)).

## Staff-session revocation and its residuals

Every staff session is bound at login to a keyed digest of the account state it was created against — `is_active`, `is_staff`, `is_superuser`, the session-auth hash and the account's effective permissions, direct and group — and `StaffSessionGuardMiddleware` recomputes that digest from **the account the session names** on every staff request, flushing the session on any difference. Disabling an account, removing its staff flag, removing one permission, changing a group's permissions, taking a member out of a group, deleting the account or changing the password therefore ends the session and deletes its row; restoring the state does not revive it, because the cookie then resolves to nothing and all 41 staff routes answer the same 302 to the login page that an expired session already produced. Reading the session rather than `request.user` is what makes the deactivated case work at all: for an inactive account the default backend resolves no user, so a guard written against `request.user` finds nothing to compare and leaves the session in place — measured, and it reproduced the old revival. Reading the database rather than relying on a signal also covers changes made with `QuerySet.update()` or a shell. Grants end sessions exactly as revocations do, while changes that cannot alter effective access (a superuser's own grants, joining a group that grants nothing) deliberately do not; a session with no digest, a malformed digest, a missing account or a non-integer identity is not trusted; and public read paths are outside the guard, answering a stale session exactly as they answer an anonymous caller. See [ADR 0213](ARCHITECTURE_DECISIONS/0213-durable-session-invalidation.md). The selected source-claim creation service now serializes its active/staff check with changes to the account row, rechecks permissions on a freshly loaded account, and rechecks the requesting session's password hash when the staff view supplies it; this still does not cancel a writer already holding the lock, serialize concurrent permission changes, or cover other writes, and a synchronized synthetic HTTP test shows a pre-authorized in-flight session can still write when the flags are disabled and re-enabled without a password change. The selected source-review, price-review, clinical-review and product-review services recheck their reviewer and, when the staff view supplies it, the session password hash after locking their target row; the product and price staging paths recheck their stager in commit mode before writing rows, clinical draft create/revise plus reference create recheck their writer before taking the draft lock, and the seven identity workspace writes recheck their writer or reviewer before their row locks. Those reads are deliberately unlocked to preserve one lock order, so a credential change committed after them still races the write, preview mode and actor-less staging are not rechecked, and a flag-only reactivation still permits a parked write. Those rechecks are a point-in-time mitigation and are **not durable revocation**: they do not end a session, and a request that passed the session guard before the state changed still runs to completion. Durable invalidation happens at the request boundary described above, and a transition that no request observes still has to be revoked explicitly. See [ADR 0192](ARCHITECTURE_DECISIONS/0192-source-claim-account-status-serialization.md), [ADR 0193](ARCHITECTURE_DECISIONS/0193-source-claim-session-hash-binding.md), [ADR 0194](ARCHITECTURE_DECISIONS/0194-source-review-actor-session-recheck.md), [ADR 0195](ARCHITECTURE_DECISIONS/0195-shared-write-actor-recheck.md), [ADR 0196](ARCHITECTURE_DECISIONS/0196-staging-write-actor-recheck.md), [ADR 0197](ARCHITECTURE_DECISIONS/0197-clinical-write-actor-recheck.md) and [ADR 0198](ARCHITECTURE_DECISIONS/0198-identity-write-actor-recheck.md). Two residuals keep this short of a complete lifecycle design. The guard fires only when a request arrives, so an off/on transition that **no** request observes leaves the bound state byte-identical and a dormant session survives it; that is why `revoke_staff_sessions` exists — a bounded, development-only command that deletes the sessions of one account or of all of them, read-only unless `--apply` — and a production revocation procedure with audit and an owner is still an open gate. Removing a backend from `AUTHENTICATION_BACKENDS` is likewise a settings change no request-time comparison can observe, a request that has already passed the guard runs to completion. `list_staff_sessions` answers the inventory question read-only: per account it reports the account flags and, per session, an alias instead of the key, whether the session is bound at all, and whether the guard would end it — which is how a dormant session becomes visible before anybody requests it. No session key, cookie value or stored digest appears in that report, and it is development-only, so a production inventory with access control, audit and retention is still an open gate. These tests do not establish an operational incident procedure, replay protection for a stolen cookie whose account state never changes, or MFA. See [ADR 0191](ARCHITECTURE_DECISIONS/0191-staff-session-revocation-gap.md) and [ADR 0213](ARCHITECTURE_DECISIONS/0213-durable-session-invalidation.md).

## Privacy and incident response

Data minimization and purpose limitation; record consent, role access, legal basis, retention and deletion/withdrawal policy with legal review. Do not put PHI in metrics, search URLs, errors or analytics. Segregate consultation data, apply per-case access and audit, and do not record audio/video by default; recording requires explicit consent and legal justification. Define incident severity, containment, notification and recovery owners before launch. Retention periods and deletion exceptions are pending legal decision, not invented here. See [runbook](OPERATIONS_RUNBOOK.md). Measured today: no severity level, acknowledgement time, notification duty, duty roster or escalation contact exists in any of the 264 documents in this repository outside this delivery, the roles and the clinical incident protocol the runbook escalates to are named in one or two documents each and defined in none, nothing detects a condition, the only signal that leaves the process is the development server's stderr, which `compose.yaml` gives no log driver, no rotation and no volume to hold, and two sweeps of all 55 routes — one anonymous, one as a fully permitted superuser — moved 0 of 33 tables and produced a `django.request` warning for every 404 and 405 and for none of the 27 successful authenticated reads, so unauthorized access to a published record would leave no trace inside this application ([the monitoring and response plan](MONITORING_RESPONSE_PLAN.md), [ADR 0237](ARCHITECTURE_DECISIONS/0237-monitoring-response-plan.md)), an unowned proposal that implements nothing.

## Actual development-slice review

`catalog/tests.py` tests XSS escaping, published-only filtering, invalid source URL rejection and GET-only methods. A development-only staff queue, bounded CSV upload, preliminary review and Django session login now exist; no production admin or patient-record feature exists. Django development server and local database, default dev secret and permissive development preview hosts are not production controls. Source validation and a boolean flag can be bypassed by bulk writes or database access; no production write path should be enabled until transactional authorization, provenance, immutable audit, separation of duties and DB constraints are implemented. Search terms can appear in server/access logs; do not enter PHI and configure logging/redaction before production. No Strix/BugHunter scan or third-party penetration test was run.

## Local staging security limitations

`stage_price_csv` is a command-line development tool, not an authenticated or authorized administration interface. `--attest-authorized` is not evidence of a legal right, user identity or approval, and the attestation it stores on the row is bound to no account. A command-line staging also writes no import receipt and no receipt items, so it appears in no import inventory, has no manifest and no per-row outcome record, and the candidate it writes can never be reviewed in the staff portal; the command is not gated on debug mode, unlike the staff portal, the projection repair and the login throttle. [The attribution gap plan](ATTRIBUTION_GAP_PLAN.md) records six costed options and seven decisions for both this and the unattributed published catalog record ([ADR 0229](ARCHITECTURE_DECISIONS/0229-attribution-gap-plan.md)); none is implemented and none has an owner. It restricts file size, row count, field names, HTTPS source URLs and source URL credentials/query strings, but cannot determine whether a source is legitimate. Only validated selected fields are persisted; operators must exclude PHI, credentials and unlicensed data. Restrict local DB, console and file access; CLI listing can expose source fields. Direct database/ORM edits bypass staging validation and append-only expectations. Before any production data use or public publication, implement access control, durable audit, source-rights governance, human review, retention, backups and independent security review.

## Opt-in synthetic login throttle

The debug-only staff login can optionally use a shared PostgreSQL per-server-address fixed-window limiter with `DAROOBANK_STAFF_LOGIN_THROTTLE=1`. It is disabled by default and outside debug, is not MFA or production protection, ignores forwarded client headers, and may block users sharing a proxy. Old pseudonymous rows require explicit synthetic-only maintenance; no scheduler or cardinality cap exists. See [ADR 0181](ARCHITECTURE_DECISIONS/0181-development-staff-login-throttle.md) before enabling it. Neither limiter is MFA, a lockout or account-aware: the unowned [MFA implementation plan](MFA_IMPLEMENTATION_PLAN.md) measures this tree — one login view, two credential fields, no factor state, no challenge store, no cryptographic library and a hash-pinned lock — prices six options for closing the gap and lists the seven decisions an owner has to make, and [ADR 0230](ARCHITECTURE_DECISIONS/0230-mfa-implementation-plan.md) records that measurement. Neither implements a factor.

## Opt-in public read limit

`DAROOBANK_PUBLIC_READ_LIMIT=1` enables a shared PostgreSQL fixed-window limit on public GETs: 120 reads per client key in a rolling minute, then 429 with an empty body, a `Retry-After` delay and the public privacy headers. It is off by default, is not load-tested, is not a production abuse control and does not replace edge rate limiting. It stores no address, path, route, query, user agent or account — one row per client key holds a digest under a scope of its own, a window start and a counter — so it cannot be joined with the login window and is not an access log. Staff paths and health probes are exempt, non-GET requests are not counted, an unavailable limiter serves the read, and nothing prunes these window rows yet ([ADR 0228](ARCHITECTURE_DECISIONS/0228-public-read-limit.md)).

## Development staff queue

`/staff/` is disabled unless debug mode is enabled. In debug mode the queue and its detail page require an active authenticated staff account with `pricing.view_pricecandidate`; neither grants editing, approval or publication. Login/logout use Django session authentication and CSRF. The staff login form refuses nonstaff users with a generic visible error, but does not revoke existing sessions or change other authentication paths; each destination must still check active/staff status and its own permissions. See [ADR 0048](ARCHITECTURE_DECISIONS/0048-development-staff-login-policy.md). Session cookies are HttpOnly, SameSite=Lax, browser-session-scoped and expire after one hour. Staff responses, including redirects and errors, are marked private/no-store/noindex, and the `same-origin` referrer policy suppresses referrers to other origins; same-origin requests can carry private paths or query strings in their Referer header and server logs. Do not use sensitive or real data. This policy permits same-origin CSRF-protected form submissions in Chromium; `no-referrer` caused an `Origin: null` rejection. Non-debug configuration uses secure session/CSRF cookies and HTTPS redirects. The slashless `/staff` root is covered by the same development gate and headers, and known slashless public search/product paths get their public privacy headers, including append-slash redirects. Known-path redirects generated early by Django's HTTPS enforcement also receive those headers; this does not change redirect or gate ordering. Redirects retain the query string, and upstream proxies and logging remain outside these headers; see [ADR 0044](ARCHITECTURE_DECISIONS/0044-slashless-privacy-boundaries.md).

This is **not a production security model**. No MFA, always-on throttling (both limiters are opt-in and off by default), account lockout, password reset flow, tamper-resistant audit trail, staff provisioning workflow or production permissions review exists. Debug error pages and public preview URLs may expose sensitive data; use synthetic data and development-only accounts. Portal activation must remain disabled until those gaps, source permissions and a security review are addressed. CLI/DB access is separate from web permissions and must be controlled by the operating system.

## Development-only staged price review risks

Price upload requires view and add permissions, explicit source-rights attestation to write, complete CSV validation and CSRF. Review requires separate view/review permissions and a different authenticated submitter; older/CLI entries without an actor fail closed. Events retain snapshots but are not database-immutable: bulk ORM writes and SQL bypass model guards. Hashes are not signatures and the source URL is outside the candidate payload hash. Rights are asserted, not verified. The application upload size check happens after Django receives the request; production needs request limits, safe temporary storage and malware handling. Measured: no rate limit exists on any public route — 48 sequential anonymous reads of six public routes all answer 200 with no `Retry-After` and no `X-RateLimit-*` header and write no row — the only limiter in the project is the opt-in, debug-only staff login window, whose single 429 carries no retry delay, `settings.py` configures no request-size ceiling, and no module answers 413 ([ADR 0223](ARCHITECTURE_DECISIONS/0223-no-abuse-protection.md)). PostgreSQL locks selected rows but product-match queries do not prevent concurrent matching insertions; conflict checks are not a concurrency guarantee. Treat all this as synthetic development functionality only, and design/test a hardened production authorization, isolation, audit and source-governance system before real use.

## Presentation read surface

HTML and JSON details share search's eligibility checks and reject unpublished, undated, incomplete or invalid-source records, including HTTPS URLs with embedded userinfo. Read-side checks reject selected control/surrogate characters in public display fields but do not constitute complete Unicode spoofing protection; see [ADR 0045](ARCHITECTURE_DECISIONS/0045-public-display-control-characters.md). Read-side checks cannot establish source legitimacy, rights or content accuracy and do not repair stale search indexes caused by bulk writes. Source URLs, including query parameters, are public; operators must not store secrets or personal information there. Detail pages are deliberately noindex/no-store, not a security boundary for published data. All non-staff routes are inventoried from the live resolver and probed for leakage of marked private rows created through the normal services, with positive controls so the absence checks cannot pass vacuously; this is literal text matching over synthetic data, not data classification, and derived, split or re-encoded private content is outside its reach (see [ADR 0202](ARCHITECTURE_DECISIONS/0202-public-route-privacy-matrix.md)).

Staff authorization was also measured for grant paths beyond direct permission grants. A group grant is equivalent to the same direct grant. **An active superuser with `is_staff` reaches all 41 staff routes without any explicit permission**, so least privilege does not constrain that account shape; a superuser without `is_staff` is denied everywhere. A deactivated account is never served content, but `AllowAllUsersModelBackend` does establish a real session for it — denial then depends on each destination checking `is_active` itself, and a future route that checked only permissions would serve content. Denials are indistinguishable across reasons and all carry the staff privacy headers. A stale in-memory actor still reports a revoked group grant while the service-level recheck denies it. See [ADR 0203](ARCHITECTURE_DECISIONS/0203-staff-grant-paths.md). Every route in that matrix, with its declared requirement, allowed methods, write classification and the suites that measure it, is collected in the [endpoint-by-endpoint authorization review](AUTHORIZATION_REVIEW.md), whose tables are generated from the live URL resolver and the pinned suites and re-rendered by a drift test rather than typed by hand (ADR 0215); the review's judgement — whether each requirement is right and whether the surface may be exposed — is explicitly unsigned.

For the 23 staff routes that take a primary key, the denial for an existing row is byte-identical to the denial for a missing one in status, body and headers (except `Date`, `Set-Cookie` and the per-second `Expires` that only the two class-based authentication endpoints stamp), and denials are identical across account shapes, so neither existence nor the reason for denial is readable from the response. Timing is **not** measured: asserting on wall-clock differences inside a test process would produce a flaky test that looks like a guarantee, and no timing-channel conclusion is drawn. Identifier shape and HTTP method were measured the same way: identifiers the URL converter accepts give one identical 403 to every unauthorized account and one identical 404 to every authorized one, so absence and out-of-range are indistinguishable, while identifiers the converter rejects give the same unmatched-URL 404 to every account including anonymous ones — a malformed identifier is therefore answered differently from a well-formed forbidden one, which reveals URL grammar but nothing about row existence. A wrong method is answered with an identical empty 405 **before** authorization on the 14 safe-only and 5 POST-only object routes, disclosing accepted methods to any authenticated account; the 4 dual-method form routes apply no method gate. Query parameters were measured the same way: nine caller-controlled shapes across all 41 staff routes cannot change an unauthorized denial, cannot produce a server error for an authorized account, cannot change the anonymous redirect and cannot widen the receipt kind filter, so a product-only account's request for a price receipt is answered byte-identically to a receipt that does not exist. The single legitimate query-driven denial is the receipt list's `kind` filter, pinned as the only one. Nine variants are a sample, not fuzzing, and no conclusion about untested parameter values follows. The CSRF gate was measured across all 43 staff routes rather than per feature: a token-less POST produces one canonical 403 for every account shape including anonymous ones and even on routes that would answer 405, so the gate runs before authentication and before the method decorators; a cross-origin POST carrying a valid token and the mangled, foreign and empty token variants are indistinguishable from it; the rejection body depends on whether the client holds a CSRF cookie and never on the account's permissions; and once a valid same-session token is presented each route answers exactly as its decorators declare, while an account without the permission still gets 403. Origin checking was exercised with one hostile origin and no Referer, so HTTPS referer validation, trusted origins and token rotation are not covered here. Session lifecycle is measured across the whole surface: an explicit logout deletes the session row rather than only clearing the cookie, a replayed pre-logout cookie is refused by all 41 routes, a password change invalidates the existing session on all 41 routes while leaving the account's status and permissions intact, and a session whose expiry is forced into the past is refused everywhere. Each walk is preceded by a positive control proving the same session worked moments earlier. This covers the **password field only**: deactivating and reactivating an account, changing permissions or groups, removing a backend or rotating a session key without touching the password still does not end an existing session, which is the open blocker recorded in [ADR 0191](ARCHITECTURE_DECISIONS/0191-staff-session-revocation-gap.md). Expiry is forced by writing `expire_date` directly, and no administrative log-out-everywhere control exists. Six HTTP methods were swept across all 43 staff routes: PUT, PATCH and DELETE are rejected with an empty 405 on every matrix route and on logout, no `Allow` header advertises a method the route does not implement, a method rejection is byte-identical for a fully permitted and a permissionless account, and an anonymous request is redirected before the method is considered. HEAD is **not** uniformly supported — the 9 dual-method and 5 POST-only routes and logout answer 405 to it because their decorators omit HEAD, an availability detail rather than an authorization one. Django's login form does accept PUT, delegating to `post`, which creates no session for an empty submission and still consumes the opt-in throttle window in both directions. TRACE and CONNECT were not sent. The complete header surface was inventoried the same way: across 1 204 staff responses (43 routes × 7 methods × anonymous, permissionless, view-only and fully permitted accounts) every response carries `Cache-Control: private, no-store, max-age=0`, `Pragma: no-cache`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy: same-origin` and the development CSP verbatim, whatever its status; `Allow` appears only on a refused method or on the OPTIONS answer of the two class-based endpoints; only the two sample downloads emit `text/csv` or a `Content-Disposition`; no status outside {200, 302, 400, 403, 404, 405, 409} occurs, so no staff route answers a wrong method or a denial with a server error; and no header outside that closed inventory appears anywhere. These headers come from three separate middlewares, so the check also proves none of them is short-circuited on any of the four status codes. Under the synthetic test settings `DEBUG` is true, so `X-Frame-Options`, HSTS and secure cookie flags are absent and are *not* exempted from the closed set; the non-debug frame policy is measured separately in fresh processes. The one response field taken straight from the request — the `Location` of a 302 — was probed with 21 caller-supplied `next` values on the login and logout endpoints and on all 41 matrix routes. Twelve hostile values (protocol-relative, absolute, single-slash, backslash, `javascript:`, `data:`, embedded userinfo, upper-cased scheme, leading space) never become a target: a successful login falls back to the staff workspace, logout to the home page, a failed login emits no `Location`, logout answers 405 to GET, and all 492 anonymous route redirects land on the login page itself with the requested staff URL as their own `next`. The login form echoes only the validated target, so a hostile value renders as an empty hidden input and no unescaped script reaches the page. Eight values Django's validator accepts are honoured verbatim after `iri_to_uri`, each with an empty netloc — including `/%2f%2fevil.example/`, which stays encoded because `urlsplit` does not decode `%2F`, and a relative target without a leading slash, which a browser resolves against the current path; both are recorded as observed behavior rather than proven safe. Because `allowed_hosts` is `{request.get_host()}`, whatever a deployment accepts as a `Host` header becomes an allowed redirect target, so this control is only as strong as host-header validation. See [ADR 0204](ARCHITECTURE_DECISIONS/0204-staff-denial-parity.md), [ADR 0205](ARCHITECTURE_DECISIONS/0205-staff-identifier-and-method-parity.md), [ADR 0206](ARCHITECTURE_DECISIONS/0206-staff-query-parameter-parity.md), [ADR 0207](ARCHITECTURE_DECISIONS/0207-staff-csrf-gate-parity.md), [ADR 0208](ARCHITECTURE_DECISIONS/0208-staff-session-lifecycle.md) [ADR 0209](ARCHITECTURE_DECISIONS/0209-staff-method-sweep.md) and [ADR 0210](ARCHITECTURE_DECISIONS/0210-staff-header-inventory.md) and [ADR 0211](ARCHITECTURE_DECISIONS/0211-staff-redirect-targets.md). No third-party assessment or production release is implied.

What those parity suites leave open — zero view permission decorators (including `3` routes whose guards live inside downstream services), active superuser `41/41` permission bypass, user/group accumulation of all 16 matrix permissions without exclusivity or lock guard, immediate-node-only separation of duties across `clinical` and `catalog` revisions, 0 of 37 database `CHECK` constraints covering actor separation, 15 of 16 `recheck_actor` sites calling `lock=False`, `4` signed cursors alongside `0` API tokens, ADR 0191's residual blockers and `5,000`-row session scan limits, `0` non-test `HTTP_X_FORWARDED_FOR` readers (referenced to lane 2's [network and TLS plan](NETWORK_TLS_PLAN.md)), 6 non-debug CLI commands outside web authorization, and live OpenAPI contract drift — is measured and priced in [the API and permissions plan](API_PERMISSIONS_PLAN.md) ([ADR 0235](ARCHITECTURE_DECISIONS/0235-api-permissions-plan.md)); no token or authorization change is implemented.

## Search cursors

Forward cursors are size-limited, timestamped and signed with the Django secret, tied to the normalized query and anchor identity, and expire after one hour. Raw queries and anchor names are not embedded: keyed digests are used, but an anchor ID remains visible. Signed tokens are not encrypted and do not provide authorization. Secret rotation, anchor deletion or changes can invalidate a cursor. Search terms and cursors can still appear in access logs; avoid personal health data and implement redaction. Application candidate validation is bounded but PostgreSQL can still scan/sort a large table, and there is no public rate limiting or production load/security assessment.

## Development product intake and review

The `/staff/products/` queue, upload and review use separate catalog permissions and the existing debug-only staff gate. Upload validates 1 MiB/1,000-row files, stores only listed structured fields, requires a source-rights assertion for staging and does not create or publish a product. Review requires a different authenticated submitter and separate permission; data integrity and sequential stale forms are checked. Source URLs are included in the candidate fingerprint. Neither the fingerprint nor the actor/rights snapshot provides tamper-proof evidence; model guards are bypassable by bulk writes and SQL. PostgreSQL locks selected rows, but simultaneous changes across the workflow are not proven safe. File limits are applied after Django receives the request; do not use real or sensitive data in the publicly reachable debug preview. Source permission, clinical review, production authorization, audit, anti-malware, request limits and independent security review remain required.

## Advisory product comparisons

Candidate comparison is available only behind the existing staff candidate-view permission and debug gate. Candidate details are already visible to that role; only eligible public presentations are included, not unpublished catalog records. Source values remain escaped and current-candidate inconsistencies suppress comparison. Ten rows per category are inspected, with truncation and skipped-invalid warnings. Neither this bound nor the index prevents database scan/sort costs, denial of service or stale data; direct/bulk writes can make indexes inconsistent or hide rows. The comparison is not rechecked or recorded when the preliminary review is submitted, so it is not a concurrency, identity, authorization or approval control. No network request is made and no security assessment or source-rights determination has been performed.

## Price comparison and suggestion safeguards

Price revision comparison is behind the existing staff-view permission and debug gate. It is limited to 10 other records with the exact source URL/ID, and verifies candidate structure and derived amounts before calculating any difference. It requires matching nonempty normalized identity fields, source name, category and unit; this is not proof of identity or rights. The URL is not covered by the existing price payload hash. Comparisons are live, not snapshotted or rechecked by review. Price matching rejects malformed/normalization-empty identifiers and treats more than 100 same-IRC indexed presentations as ambiguous, not a unique match. Stale indexes, direct DB writes, concurrent changes and DB scan/sort costs remain unresolved; no rate-limit, production security or source-rights validation follows from these safeguards.


## Development-only source assertions

The `/staff/sources/` portal is disabled outside debug mode and requires an active staff account with `sources.view_sourceclaim`. Adding a claim also requires `sources.add_sourceclaim`; independently reviewing another user's claim requires `sources.review_sourceclaim` plus view. CSRF and staff privacy headers apply. Product and price details do not expose claim data to users without the separate source view permission. Source and evidence URLs reject credentials, query and fragment, but users can still enter sensitive text elsewhere; use only synthetic data in this debug portal. The server does not fetch URLs. The ledger is not an authorization gate, source verification, a legal decision or an audit system. Its hashes omit actor/time and provide no signature; bulk ORM/SQL bypass model guards, and full concurrent review behavior is unproven. Existing production-security gaps, MFA, throttling, tamper-resistant audit and legal review remain prerequisites.


## Window inspection and shared validation

The development-only schedule page is GET/HEAD-only, uses the normal privacy/debug gate and requires active staff with at least one product, price or source view permission. It performs no source/network operation, settings write or dispatch. The local management command bypasses web authorization, so restrict OS access; it likewise only computes. Timezone boundaries are rejected if ambiguous or nonexistent. The utility relies on host clock/tzdata and does not authorize ingestion. The shared private-intake URL validator rejects empty credential markers, query/fragment delimiters (including empty ones), controls and invalid Unicode. It is not an SSRF safety policy or network authorization, and existing public presentation URL behavior is separate. Invalid control/surrogate characters in new review reasons are rejected. Bulk ORM/SQL still bypasses service validation.


## Development-only web intake receipts

Successful web product/price staging and its receipt use one database transaction. Read access is scoped by the corresponding candidate view permission, with domain filtering before count, pagination and detail lookup; source-only users have no receipt access. The staff debug gate, private headers and CSRF-protected staging still apply. Receipt source URL and actor are unverified assertions; no raw file, filename or file-level hash is retained. New receipt manifests retain source record IDs, candidate hashes and references; this is additional sensitive metadata and must remain synthetic in this debug system. Preview, failure, CLI/original-importer and imports before receipts have no receipt; earlier receipts have no row manifest, so this is not a complete or tamper-resistant audit. Local code can call the receipt wrappers directly with an authorized user, outside the web debug gate; restrict OS and database access. Bulk ORM/SQL bypass guards, permissions can be modified without audit and production concurrency/crash safety is not established. Do not use real source data or credentials in the debug portal.


Row manifests are domain-scoped through the receipt lookup; structural and per-row checks suppress inconsistent links, but do not establish authenticity or integrity against a database writer. Candidate pages show at most five recent distinct same-domain receipt clues; their presence/absence proves nothing about source rights or complete history. Foreign keys use `PROTECT`; `QuerySet.update/delete` and SQL still bypass model guards, and retention/deletion/repair remain undefined. Price hashes omit source URL. No real personal or proprietary data should be entered into this debug workflow.


## Development-only clinical drafts

The clinical queue and its create/revise/review routes are under the normal debug-only staff gate and use separate `clinical.view_clinicaldraft`, `clinical.add_clinicaldraft` and `clinical.review_clinicaldraft` permissions. Review also requires view and a reviewer distinct from the draft author and all current supplementary-reference recorders. CSRF and private/no-store/noindex and same-origin referrer headers apply (private URLs can reach same-origin logs, not external sites); source-claim hints require independent source view permission. The form's synthetic-data checkbox is an assertion; the app cannot prevent a user from entering patient or copyrighted information, and direct services bypass the web debug gate. Use only isolated synthetic data. URLs are validated but never fetched. Draft hashes omit author/time and are not signatures; bulk ORM/SQL can alter history and full concurrency behavior is not proven. Review is not approval; no public clinical route or publication exists. Qualified review, retention, privacy, durable audit and production security remain unresolved.


Supplementary clinical assertions use the same separate clinical view/add permissions and the normal staff CSRF/debug/private gates. No source is fetched. New review snapshots contain the bounded supplementary reference metadata and recorder IDs; access and retention need consideration even though the development portal must only contain synthetic data. Sequential evidence-set mismatches, malformed snapshots and over-limit assertion sets fail closed in the application, but assertion payload hashes do not cover recorder/time, while set hashes include recorder IDs but not timestamps; neither is a signature. PostgreSQL row locks do not protect direct writes, and bulk ORM/SQL bypasses prevent claims of tamper-resistant audit. Direct service calls are outside the web debug gate.

## Cooperative staging locks

Product and price committed CSV staging uses PostgreSQL transaction advisory locks keyed by domain and exact source URL; previews do not lock. Receipt/manifest writes are inside the outer transaction. Only writers using the current services participate; older processes, ORM bulk operations and SQL can bypass the protocol. A long transaction or callback can make other same-source requests wait, and the service does not set a lock timeout or retry policy. Selected PostgreSQL concurrency errors are translated after staging/receipt rollback into a generic conflict; connection loss and later enclosing-transaction commit remain outside this boundary. See [ADR 0055](ARCHITECTURE_DECISIONS/0055-staging-conflict-boundary.md). This protects neither source authorization nor matching against concurrent catalog changes, and does not create immutable or exactly-once audit records. See [ADR 0010](ARCHITECTURE_DECISIONS/0010-staging-concurrency.md).


## Indexed IRC inspection

The DEBUG-only indexed IRC clue page uses `catalog.view_productpresentation` and can reveal IDs and status for unpublished presentations; group permissions apply. It does not intentionally render source names, URLs or IRC values. Its signed cursor contains IDs and a keyed digest; it is not encrypted, not an access grant and can be guessable when a known debug secret protects low-entropy codes. Cursor URLs may be logged. The local command/service operate outside the web gate. A stale or corrupt index can hide matching records and results are not a snapshot, evidence, authorization or identity verification; use synthetic data only. See [ADR 0011](ARCHITECTURE_DECISIONS/0011-indexed-irc-inspection.md).
